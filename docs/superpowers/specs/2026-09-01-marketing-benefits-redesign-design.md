# 营销福利额度、删除能力与双模板重设计

## 状态

- 日期：2026-09-01
- 阶段：设计已根据交互渲染稿获得用户确认，等待设计文档复核
- 范围：福利活动、用户福利券、券流水、兑换码、优惠码；Default 与 Classic 两套前端
- 不包含：生产环境部署、现有消费计费顺序调整、活动分组绑定语义调整

## 背景

当前实现把福利活动配置金额固定解释为人民币元，同时在报表中通过活动总金额与
`total_quota` 的比例反推已用和剩余金额。用户券页又混合展示格式化额度与原始 quota 数字，
导致同一张券在不同页面使用不同口径，且无法随系统 `quota_display_type` 一致切换。

营销资源的删除体验也不完整：兑换码已有多选但缺少“删除所选”，优惠码缺少多选和批量
删除，福利活动缺少明确的历史活动删除入口。券列表和流水只有最小字段堆叠，不适合运营
查询与对账。

## 目标

1. 所有面向用户和管理员的福利额度都基于实际内部额度余额，并按系统当前展示类型格式化。
2. 页面不展示原始 quota 数字或把 quota 当作用户理解的单位。
3. 福利活动、兑换码、优惠码提供一致的单条/批量删除体验，并保留必要审计与历史关联。
4. 券列表、流水和用户活动福利页采用已确认渲染稿的信息结构。
5. Default 与 Classic 保持相同产品能力，但分别复用各自组件体系。

## 非目标

- 不改变福利抵扣的顺序：福利券仍先于订阅和钱包。
- 不把福利额度合并到用户钱包。
- 不删除消费日志、优惠码使用记录、券流水或已经发生的支付/领取审计。
- 不用新的货币账本替换全站内部 quota 计费体系。
- 不要求 Default 与 Classic 共用 React 组件源码。

## 术语与核心决策

### 真实额度

“真实额度”指实际参与预扣、结算和退款的内部额度余额：

- 活动：`total_quota`、`distributed_quota`、`used_quota`、`expired_unused_quota`。
- 券：`original_quota`、`used_quota`、`remaining_quota`。
- 流水：`quota_delta`、`balance_after`。

这些字段仍是后端计费的 Source of Truth，但前端只能通过统一额度格式化器展示，不得直接
输出 quota 数字，也不得通过固定人民币金额比例反推。

### 当前额度展示类型

页面读取系统状态中的 `quota_display_type`、`quota_per_unit`、`usd_exchange_rate`、
`custom_currency_symbol` 和 `custom_currency_exchange_rate`：

- `USD`：展示美元符号和金额。
- `CNY`：按当前美元兑人民币汇率展示人民币。
- `CUSTOM`：按自定义符号和汇率展示。
- `TOKENS`：展示 Tokens 数量，不使用货币符号。

系统切换展示类型后，活动报表、券列表、流水和用户福利页应随下一次渲染/刷新统一切换。
历史使用量不因展示类型变化而改变，只有展示值变化。

### 活动配置金额

创建和编辑活动时，管理员按系统当前展示类型填写总预算、固定/随机面额和领取门槛：

- 货币类型允许最多两位小数，最小步进为 `0.01`。
- `TOKENS` 类型只允许整数，最小步进为 `1`。
- 前端发送当前 `amount_display_type`；服务端必须与提交时的当前系统设置核对，设置已变化时
  拒绝保存并提示管理员刷新，避免用旧汇率或旧单位提交。
- 服务端使用 decimal 和当前配置把展示金额转换为内部 quota，所有上限与饱和规则继续使用
  `common/quota_math.go` 的安全转换能力。

领取门槛是历史实际支付金额，不是可消费额度。表单仍按当前展示类型填写，但服务端需单独
换算为 CNY 支付快照，与现有统一归一为 CNY 的充值实付金额比较；不得把领取门槛存成或
比较成 quota。`TOKENS` 展示下输入的门槛先按当前站点额度换算得到等价金额，再保存 CNY
门槛快照。

数据库中现有 `*_cents` 是旧人民币配置快照，不再作为报表或券余额的运行时真值。迁移后
活动的可用配置应以内部额度字段为准；旧字段只用于一次性迁移和历史审计，不能继续被新
页面读取。

## 数据模型

### 福利活动

活动保留 `TotalQuota` 作为总预算真值，并增加内部额度配置字段：

- `FixedQuota`
- `MinQuota`
- `MaxQuota`
- `AmountDisplayTypeSnapshot`
- `AmountDisplayRateSnapshot`
- `QuotaPerUnitSnapshot`
- `DeletedAt`

快照字段只用于解释“创建时管理员填写的单位和换算环境”，不参与当前页面金额展示。
发布后的 `BenefitActivityShare.Quota` 继续是每份券的最终额度真值。

`ClaimPaidThresholdCents` 继续保存 CNY 实付门槛，因为全站历史充值实付金额已经归一为 CNY；
API 和页面按当前展示类型转换输入与回显，但资格比较始终使用同一 CNY 业务口径。

旧活动迁移原则：

1. 已发布活动优先依据现有 `TotalQuota` 和已生成 share 的 `Quota`，不得重新按当前汇率计算。
2. 草稿活动根据旧人民币金额和迁移时记录的历史语义生成内部额度配置。
3. 无法无损推导的异常记录停止迁移并记录错误，不静默补零。
4. 迁移兼容 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。

### 福利券与流水

`BenefitUserVoucher` 和 `BenefitVoucherLedger` 不新增第二套可变金额余额。原始、已用、剩余、
变更量和变更后余额继续由 quota 字段唯一表达，API 响应提供足够的活动、用户和时间信息供
页面格式化与对账。

券列表需要补充或关联返回：

- 活动名称与分组快照
- 用户 ID 和可展示用户名
- 领取时间、失效时间、作废时间与原因
- 原始/已用/剩余额度
- 券状态

流水需要补充或保留：

- 类型、`quota_delta`、`balance_after`
- `request_id`、`log_id`
- 操作人/作废原因等受权限保护的元数据
- 创建时间

## 删除契约

### 通用规则

- 删除采用 GORM 软删除，不物理清除业务历史。
- 单条和批量删除都使用管理员鉴权、关键操作限流和管理审计。
- 批量请求对 ID 去重，拒绝非正数和超过上限的数组。
- 数据库错误时整批事务回滚；业务状态不允许删除的条目以 `skipped` 返回，不影响其余合法项。
- 响应返回 `deleted_ids` 和 `skipped: [{id, reason}]`，前端必须展示实际结果，不能只提示
  “操作成功”。

### 福利活动

接口：

- `DELETE /api/benefit/admin/activities/:id`
- `DELETE /api/benefit/admin/activities/batch`，请求体 `{ "ids": [1, 2] }`

允许删除：

- `draft`，且尚未生成领取数据。
- `ended`，在事务内完成过期归一化后没有 active 券。
- `terminated`，且没有仍可使用的 active 券。

拒绝删除：

- `published` 或 `paused`。
- `terminate_mode=unused` 且仍有可使用券的活动。
- 存在未完成额度事务或其他会破坏结算的状态。

删除活动只让活动从常规列表和用户可领取列表中消失。share、已领取券和流水继续保留；
管理员从券历史进入时通过 `Unscoped` 读取活动快照，以保证对账信息完整。

### 兑换码

接口：

- 保留单条 `DELETE /api/redemption/:id`。
- 增加 `DELETE /api/redemption/batch`。
- 保留 `DELETE /api/redemption/invalid`，清理已使用、已禁用和已过期记录。

兑换码软删除后不再可兑换；既有充值日志、用户到账结果和返佣来源保持不变。

### 优惠码

接口：

- 保留单条 `DELETE /api/promo_code/:id`。
- 增加 `DELETE /api/promo_code/batch`。
- 增加 `DELETE /api/promo_code/invalid`，清理已禁用、已用尽和已过期记录。

优惠码继续使用 `deleted_id + deleted_at` 释放代码唯一键。删除前已建立的支付预留允许通过
`Unscoped` 完成回调结算；删除后不得创建新的预留或新订单。

## API 与前端金额契约

后端 API 继续返回内部额度数值，前端统一使用共享 formatter：

- Default：复用 Default 额度展示工具和状态 Store，不在 feature 内创建私有换算公式。
- Classic：复用 `renderQuota`、`quotaToDisplayAmount` 和 `getCurrencyConfig`，页面不得写死
  `¥`、`$` 或人民币文案。

活动报表取消 `reportAmountFromQuota` 这类“总金额比例反推”逻辑，直接格式化报表实际额度。
券列表和流水也不再展示 `original_quota`、`used_quota`、`remaining_quota` 的裸数字。

活动配置 API 的金额字段仍采用面向管理员的数值名称，但增加 `amount_display_type`。响应同时
提供内部额度配置，前端根据当前展示类型回显。旧人民币 `*_amount_cents` 字段不再是新前端
合同。

## 已确认的页面设计

### 用户活动福利页

- 顶部四项摘要：可用福利、已使用、即将到期、可领取活动。
- “我的福利券”卡片突出剩余额度、使用进度、状态、领取/失效时间、绑定分组和流水入口。
- “可领取活动”卡片展示份额、每份额度、个人有效期、资格状态和领取按钮。
- 桌面端双列，窄屏单列；状态和操作不能挤成一行原始文本。

### 后台活动管理

- 统计摘要、搜索/状态筛选、活动表格、选择工具栏和分页置于统一业务面板。
- 历史活动可多选；选择后出现批量删除工具栏。
- 进行中活动的删除入口禁用，并明确“先结束或终止”。
- 行内其他操作继续聚合到操作菜单。

### 券列表

- 字段：券 ID、活动/分组、领取用户、原始额度、已使用、剩余、状态、领取时间、失效时间、
  操作。
- 支持活动、用户、状态筛选和导出。
- 批量作废只对可用券开放；删除券不在本期范围内。
- 移动端使用信息卡片，保持同一字段和操作能力。

### 券流水

- 左侧/顶部为券余额摘要和基础信息，右侧/下方为时间线或明细表。
- 每条流水展示业务类型、格式化变更额度、变更后余额、请求/日志关联和时间。
- 管理员可见作废原因及操作人；普通用户不显示管理员元数据。

### 兑换码与优惠码

- 两类资源采用同一布局骨架：筛选、统计、可选表格、批量工具栏、分页。
- 兑换码保留复制所选和清理失效，并新增删除所选。
- 优惠码新增多选、删除所选和清理失效。
- 删除确认必须说明影响范围和保留的审计记录。

## 模板边界

- Default 使用 shadcn/Base UI、TanStack Table、现有批量操作工具栏和确认对话框。
- Classic 使用 Semi UI 的 Table、Card、SideSheet、Dropdown、Modal 和既有 Classic 面板样式。
- 两套模板共享 API、字段语义、状态规则和 i18n 文案含义，不共享组件实现。
- 本次同时修改并分别验证 Default 与 Classic；不能以其中一套通过替代另一套验收。

## 错误与并发处理

- 删除请求在后端事务中重新读取并锁定目标，不能信任前端状态。
- 批量删除返回实际删除和跳过结果；重复请求应幂等。
- 活动删除与领取/结算并发时，以行锁后的最新活动、券和流水状态判定。
- 优惠码删除与支付回调并发时，已有 reservation 可结算，新 reservation 被拒绝。
- 页面请求失败保留当前选择并显示可操作错误；成功后清空已删除项并刷新当前页。
- 删除后当前页为空时自动回退上一页，避免显示空白分页。

## 审计与安全

管理审计事件至少包括：

- `benefit.activity.delete`、`benefit.activity.delete_batch`
- `redemption.delete`、`redemption.delete_batch`、`redemption.delete_invalid`
- `promo_code.delete`、`promo_code.delete_batch`、`promo_code.delete_invalid`

审计记录操作人、实际删除数量、跳过数量和资源 ID；不记录兑换码/优惠码完整明文、用户隐私
或支付凭据。

- 活动、券和流水不出现裸 quota 或写死人民币符号。

## 回滚

- 前端可回滚到旧列表，但后端新增软删除列和额度快照列保留，不做破坏性降级。
- 回滚后旧客户端不得读取已废弃的固定人民币字段作为新活动真值。
- 若迁移或转换验证失败，在更新任何活动前停止启动迁移并保留原记录。
- zzapi 回滚使用部署前 Compose 备份和上一已验证镜像；生产回滚必须单独获得授权。

## 已确认视觉稿

交互稿包含用户端福利、活动管理、券列表、流水和兑换码/优惠码五个视图，支持额度展示类型
切换、批量选择和删除确认。用户已确认按该布局方向实现。
