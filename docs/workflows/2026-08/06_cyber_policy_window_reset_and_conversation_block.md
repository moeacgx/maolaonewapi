# 官方风控封禁窗口重置与会话阻断

## 问题

`cyber_policy` 自动封禁原先直接统计滚动窗口内的全部历史事件。Root 手动恢复用户后，
上一次封禁前的事件仍在窗口内，用户下一次命中可能立即再次被禁用。

上游明确拒绝当前对话后，网关也只处理本次响应。客户端继续使用同一稳定会话标识发起
请求时，仍会再次占用渠道并调用上游。

## 方案

- `users.cyber_policy_count_reset_event_id` 保存最近一次自动封禁成功时的累计重置事件 ID。
- 禁用普通用户的同一条条件更新同时写入状态和重置点；重置点取本次累计查询中最新的
  已计入事件 ID，并发命中只有成功完成状态迁移的执行者能够更新重置点和记录处置日志。
- 审计事件继续完整保留。单用户自动处置和事件列表批量计数都只统计重置点之后的新
  事件，仍叠加当前滚动窗口、渠道或分组范围及自动封禁白名单。
- 精确识别到上游 `cyber_policy` 后，将 `用户 ID + 稳定会话来源 + 稳定会话值` 做
  SHA-256 后写入混合缓存，原始会话标识不落库、不写日志。
- 后续同用户、同会话请求在选渠、并发占用和计费前返回 403；不同用户即使提交相同
  会话值也不会互相影响。
- 只接受稳定会话头、`prompt_cache_key`、`conversation_id`、
  `conversation`/`conversation.id` 和明确的会话元数据。`request_id`、
  `previous_response_id`、消息正文和首条提示词均
  不作为会话身份，避免把相似内容或变化中的响应 ID 误判为同一对话。

## 兼容性与边界

用户表通过 GORM 新增普通整数时间列，默认值为 0，兼容 SQLite、MySQL 和 PostgreSQL；
旧用户保持原有统计语义，首次自动封禁后才建立重置点。

会话标记有效期使用当前官方风控滚动窗口。Redis 可用时多实例共享；未配置 Redis 时
回退到单实例有界内存缓存，进程重启或缓存淘汰后标记不会保留。缓存读取故障按可用性
优先记录错误并放行，不能因缓存基础设施故障阻断所有会话。没有稳定会话标识时只保留
本次上游拒绝，不进行推测性会话拦截。

## 验证

- 达到阈值后用户状态和重置点同时更新，历史审计事件数量不变。
- 手动恢复后旧事件计数为 0，第一次新命中计数为 1 且不会立即再次禁用。
- 相同用户和稳定会话标识命中拦截；不同用户、不同会话不命中。
- Codex 稳定会话头与请求体 `prompt_cache_key` 都可识别。
- 只有 `previous_response_id` 或普通正文时不建立会话标记。
- `go test -count=1 -timeout 60s ./model ./service ./controller`。
