# 计费预留补偿一致性

## 问题与目标

统一计费会话和 Realtime 兼容路径都先扣令牌额度，再预留钱包或订阅额度。
此前资金来源写入失败后会直接执行一次 `IncreaseTokenQuota`；如果这次回滚也失败，
会话会丢弃这笔令牌扣减。初始预扣会清零本地状态，增量预留也不会把失败额度带入
后续结算，最终可能永久少退令牌额度。

另一个独立问题是订阅增量预留把 `PostConsumeUserSubscriptionDelta` 的所有错误都包装为
`insufficient_user_quota` 和 HTTP 403。数据库查询、行锁、更新或事务提交故障因此会被
误报为用户额度不足，并被禁止记录错误日志。

本次修复目标：

- 令牌补偿可使用同一操作键安全重放，不直接重复非幂等的 `quota += N`；
- 临时失败在请求内重试，持续失败进入数据库待处理状态并由后台 Worker 恢复；
- Realtime 已经进入成功 usage 结算后，后续 `Refund` 不得改成全额退款；
- 只有明确的订阅业务错误返回 403，所有未知订阅写入错误失败关闭为 503。

## 令牌补偿账本

新增 `token_quota_compensations` 表：

- `operation_key`：调用方操作键的 SHA-256，唯一索引；
- `token_id`、`quota`：补偿载荷，同一键重放时必须完全一致；
- `status`：`pending`、事务内临时 `applying`、`applied`；
- `cache_invalidated`：数据库补偿完成后，Redis 令牌缓存是否已确认失效；
- `created_at`、`updated_at`：恢复扫描和清理时间。

非批量模式的执行顺序：

1. 使用 `ON CONFLICT DO NOTHING` 跨数据库创建 `pending` 记录；
2. 在同一数据库事务中条件认领记录、增加令牌额度并将记录改为 `applied`；
3. 事务提交结果未知时，在新事务中查询相同操作键；只有完全一致且已经 `applied`
   才确认成功，不能盲目重复额度更新；
4. 提交后失效 Redis 令牌缓存，再将 `cache_invalidated` 标记为 `true`；
5. 缓存失效失败时，同键重放只再次失效缓存，不重复增加数据库额度。

普通的非批量令牌增减也改为先确认数据库更新成功，再异步调整 Redis；数据库明确返回失败
时不再提前改变缓存额度。数据库提交结果未知时仍按下文的结算边界处理，不能盲目重放。

批量模式保持现有实时额度权威，但不再让刷盘与资金预留竞态：令牌扣减会先取得按令牌
分片的刷盘锁，并返回可提交或可取消的预留句柄。资金预留成功后才同步更新 Redis 并
释放刷盘锁；资金预留失败时，句柄在同一批量队列中加入等额反向增量后再释放锁。因此
刷盘只能看到已提交扣减或已经抵消的净值，资金预留失败不会留下仅令牌侧落库的扣减。
资金预留成功后、令牌批量队列刷盘前进程退出的反向窗口仍属于既有批量模式限制，本次
热修不把内存队列提升为跨进程账本。

批量刷盘会把正在处理的令牌差额保留在 `in_flight` 内存状态；数据库更新失败时差额放回
待处理队列，不再像旧实现一样只记录日志后丢弃。批量模式下资金失败的扣减尚未落库，
所以原地抵消不创建补偿记录；已经存在的历史 `pending` 记录仍由 Worker 直接落库处理。

Worker 每 30 秒扫描 `pending` 或尚未确认缓存失效的记录；已完成并确认缓存失效超过
7 天的记录每小时清理一次。多实例可同时扫描，同一操作键通过条件认领和数据库事务
保证只应用一次。SQLite 使用其写事务串行化，MySQL 和 PostgreSQL 使用相同的 GORM
条件更新，不依赖数据库驱动错误文本。

## 会话状态

`BillingSession` 为初始预扣和每个累计预留目标生成稳定补偿键。键由请求标识、会话唯一值、
阶段和目标额度共同组成：同一次补偿重放保持不变，重新创建的会话即使复用请求标识也不会
误认成已经完成的旧补偿。补偿在请求内最多尝试三次；第一次失败但后续成功时，错误链仍
保留原失败供诊断，余额已经恢复。连续失败时，会话保留待补偿操作并异步重试。非批量模式
在 `pending` 记录已经成功创建后允许进程重启继续恢复；批量模式在释放刷盘锁前原地抵消，
不依赖重启后的补偿记录。

`Settle` 首次调用固定不可变的结算目标；再次使用不同目标会返回冲突。结算前先完成
待补偿令牌操作；结算开始后不再接受新的累计预留。Realtime 已进入结算意图后，控制器
错误清理阶段调用 `Refund` 只允许继续补偿，不能把已经发生的成功 usage 切换为全额退款。

资金来源和普通令牌结算写入没有持久幂等终态，因此失败后不会由后台自动重放，避免数据库
提交结果未知时造成重复扣费。同一会话仍保留首次结算目标和已确认完成的步骤，后续显式恢复
只能使用相同目标；生产恢复前必须先核对数据库和实时额度状态。

这张账本只处理“令牌已扣、资金未扣”的补偿，不改变普通成功结算和普通请求退款的
既有额度写入模式。结算资金或令牌调整自身失败后的跨进程终态恢复、普通钱包退款的
提交结果未知语义不在本次热修范围内，不能把这张补偿表当作完整计费账本。

## 订阅错误语义

模型层新增两个业务哨兵：

- `ErrNoActiveSubscription`；
- `ErrSubscriptionQuotaInsufficient`。

只有 `errors.Is` 命中上述哨兵时返回 HTTP 403 和 `insufficient_user_quota`，并保持
`SkipRetry`、不记录错误日志。错误文本恰好包含相同英文短语但没有包装哨兵时不得视为
业务不足。

活跃订阅查询、订阅行查询、行锁、保存和事务提交错误保留原始错误链，返回 HTTP 503、
`update_data_error` 和 `SkipRetry`，允许记录本地错误。`HasActiveUserSubscription` 的查询
故障返回 HTTP 503、`query_data_error`，不得回退钱包。

## 数据库与部署兼容

- 表结构和查询均使用 GORM，支持 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+；
- 唯一冲突使用 GORM `OnConflict DoNothing`，不会用唯一键错误文本判断结果；
- 无破坏性迁移，升级时自动创建补偿表；
- 回滚代码前应先确认没有 `pending` 或 `cache_invalidated = false` 的记录，否则旧版本不会
  继续处理这些补偿任务。

## 验证

- 初始钱包预扣和 Realtime 增量预留在第一次令牌补偿失败后安全重放，余额只恢复一次；
- 连续补偿失败会保留 `pending`，后续结算或 Worker 恢复后余额守恒；
- 相同操作键重复执行不重复增额，载荷不同返回幂等冲突；
- 相同请求标识下重新创建的计费会话使用不同补偿键，不会漏掉第二次实际回滚；
- 数据库写入失败后记录保持 `pending`，恢复扫描可完成操作；
- 批量预留与刷盘并发时，资金失败仍只抵消一次且数据库余额不变；
- 批量刷盘失败后差额回到待处理队列，故障恢复后只落库一次；
- 清理任务只删除超过保留期、已应用且缓存失效完成的记录；
- 相同结算目标可重复调用，不同目标被拒绝；结算开始后 `Refund` 不执行全额退款；
- 订阅业务不足返回 403，伪造同名文本和数据库故障返回 503；
- 统一计费和 Realtime 兼容路径在非批量模式使用持久幂等补偿，在批量模式使用锁内原地抵消；
- 执行模型、服务、Relay 定向回归、格式化、`go vet` 和 `git diff --check`。
