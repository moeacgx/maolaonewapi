# 三容器渠道并发统一计数

## 目标

渠道的 `concurrency_limit` 表示所有应用容器合计的正在处理请求数，而不是每个容器各自允许的数量。
例如渠道上限为 `18` 时，`maolaoapi`、`maolaoapi-slave-1` 和 `maolaoapi-slave-2` 的占用总数达到
`18` 后，三个容器都必须拒绝新的该渠道请求。

## 根因

早期实现使用 Go 进程内 `map[int]int` 保存渠道占用。三个容器各自拥有一份 map，导致每个容器都能独立
占满配置上限，合计值最高可能达到容器数乘以上限。单进程重启还会丢失占用状态，异常退出则无法回收
请求槽位。

## 实现契约

- Redis 开启且渠道配置了正数上限时，使用共享 Redis Sorted Set：每个渠道一个 key，每个请求一个唯一租约
  token，score 是租约过期时间。
- Lua 脚本在 Redis 内原子完成过期租约清理、当前占用判断和新租约写入，避免“先检查再占用”的竞态。
- 请求结束按租约 token 精确删除；禁止按渠道 ID 做释放，否则一个请求可能误释放另一个请求的槽位。
- 长请求按 `2` 分钟 TTL 的三分之一周期续期。Redis 使用服务器时间计算过期时间，避免三个容器系统时钟
  不一致导致租约提前失效。
- Redis 开启但不可用时，有限并发渠道 fail-closed；不得回退成每容器本地计数而突破全局上限。
- Redis 未启用时保留进程内租约 map，仅作为单实例部署和单元测试回退；它不提供跨容器合计能力。
- `nil` 或 `0` 并发上限仍表示不限，不创建 Redis 租约。

## Redis 配置边界

三个应用容器必须使用同一个 `REDIS_CONN_STRING` 目标，包括相同的 Redis 服务、端口、认证信息和逻辑数据库
编号。Redis 前缀为 `new-api:channel-concurrency:`，不要在不同环境之间复用同一 Redis 逻辑数据库。

Redis 中的租约是运行时状态，不迁移到数据库。进程正常结束会主动释放；进程崩溃、网络中断或主机掉电时，
租约最多保留到 TTL，之后由下一次检查或抢占自动清理。

## 选择与错误

选择器的可用性检查只用于筛选候选，最终准入仍由 Redis Lua 原子抢占决定。检查和抢占之间如果被其他容器
占满，当前请求会继续走现有的渠道重选逻辑；所有候选都满时返回错误码 `channel_concurrency_limit`。
简体中文用户文案为“当前渠道并发已达到上限，请稍后重试”，英文文案保持独立翻译，不向用户暴露内部
哨兵错误文本。

## 发布与排障

1. 发布前确认三个 Compose 服务使用同一 Redis 目标，并确认 Redis 可写、可执行 Lua 和时间命令。
2. 先更新一个应用容器，观察健康状态、Redis 租约 key 和 `channel_concurrency_limit` 错误，再继续下一个。
3. 更新顺序固定为 `maolaoapi`、`maolaoapi-slave-1`、`maolaoapi-slave-2`，每个容器健康后再进行下一个。
4. 排查渠道 `267` 时，检查 Redis 对应 Sorted Set 的成员数和过期 score，结合请求日志判断是真实占用还是
   超时租约；不要只查看单个容器的本地进程指标。
5. Redis 故障期间不要通过关闭并发检查来恢复流量，否则会让三个容器合计突破上限；先恢复共享 Redis。

## 回归验证

- 两个独立 Redis 客户端模拟两个容器：容器 A 占用 `10`，容器 B 占用 `8`，上限 `18` 时第三次占用失败。
- 精确释放 A 的一个 token 后可以补进一个新租约，错误 token 不能释放其他请求。
- 租约 TTL 到期后，下一次可用性检查会清理过期成员并恢复槽位。
- Redis 连接失败时有限渠道的占用和可用性检查均失败关闭。

- `cd relaykit && GOWORK=off go build ./...`
- `gofmt`、`git diff --check`
