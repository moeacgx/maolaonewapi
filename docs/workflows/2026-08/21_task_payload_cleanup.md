# 任务正文历史残留清理

## 目标

清理生产 PostgreSQL `new-api.tasks` 中已完成且结束超过一小时的任务正文，
避免历史 JSON 正文继续被任务查询读取。任务行本身保留，用于账务、状态和审计。

## 范围

- 仅将满足以下条件的 `tasks.data` 置为 `NULL`：`status` 为 `SUCCESS` 或
  `FAILURE`、`finish_time` 已设置、且结束时间早于当前时间一小时以上。
- 不删除任务行，不修改 `properties`、`private_data`、账务字段、状态或时间戳。
- 本次按用户确认的“旧任务正文”范围处理了 23 条终态记录；其中包含历史
  上游任务平台记录，不限于本地 `image`/`canvas_image` 包装平台。
- 最近一小时内的 7 条非空正文未处理。

## 验证结果

- 更新事务返回 `cleared_rows = 23`，提交成功。
- 复核显示老于一小时的终态非空正文为 `0`；仍有 7 条近期或未完成正文，合计
  约 1.4 KiB。
- `maolaoapi` 容器仍为 `running/healthy`，PostgreSQL 容器为 `running`。
- 清理前 `tasks` 约 14 GB，其中 heap 约 8 MB，主要为 PostgreSQL TOAST 历史空间；
  清理后表文件仍约 14 GB，这是预期行为，删除/置空行不会立即缩小物理文件。
- 主机根文件系统约 1 TB，总可用空间约 843 GB；本次未执行 `VACUUM FULL`、
  `pg_repack`、停机或表重写。

## 后续风险

- 当前代码的自动正文保留清理只覆盖本地 `image`/`canvas_image` 平台；历史
  上游异步平台是否能在一小时后清理，仍需单独设计并验证视频代理和结果 URL
  依赖，不能直接扩大现有清理条件。
- 若需要回收已经空闲的 14 GB 物理空间，应在维护评估后执行 `pg_repack` 或
  其他表重写方案；执行前需确认额外临时磁盘、锁等待和备份策略。
