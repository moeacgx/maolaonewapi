# 用户额度同步窗口无感等待

## 问题与目标

批量额度正在持久化时，缓存读取会主动失败关闭，避免请求使用尚未确认的旧额度。
此前普通中继请求直接把该内部同步状态包装成 HTTP 500，导致正常的短暂落库窗口影响用户请求。

本次调整的目标是在不放宽额度一致性保护的前提下，让用户请求等待同步完成后自动继续。

## 实现范围

- 新增带请求上下文的额度与完整用户缓存读取入口
  `GetUserQuotaWithContext`、`GetUserCacheWithContext`；
- 会话鉴权、只读令牌鉴权和普通令牌鉴权在额度持久化窗口内等待缓存恢复，
  避免请求在进入中继计费前就被拒绝；空令牌 Key 在进入缓存或数据库查询前直接按无效令牌拒绝，
  不会退化为读取第一条令牌；
- 普通预扣费、统一计费会话、WebSocket 预扣费、Midjourney 提交与 OpenAI 兼容额度查询
  改用带等待的读取入口；
- Redis 中已有身份完整、额度可信的实时快照时，普通数据库刷盘期间继续直接读取，
  不再因为本实例处于 `inProgress` 状态阻断用户请求；
- 缓存缺失、额度不可信或存在 deferred fallback 时继续失败关闭，数据库回退必须经过
  generation 栅栏确认，不能读取尚未包含待落库增量的额度；
- 仅对错误链中明确包含 `ErrUserQuotaCacheSync` 的故障进行等待和重读；普通 Redis、数据库或
  订阅事务 deadline 保持原始错误语义，不会被误报成额度同步超时；
- 请求取消时立即停止等待；鉴权后续控制器优先复用请求 Context 中的额度、分组和用户设置，
  只有匿名、session-only 或查询其他用户时才回退读取缓存；
- 跨实例回退锁探测按用户使用 `singleflight` 合并，并从 20ms 逐步退避到 250ms，
  单次 Redis 探测最多等待 1 秒，避免大量等待请求挤满默认连接池；
- 写侧遇到其他实例持有 fallback 锁时只判定一次，随后立即进入受保护的数据库回退，
  不再执行 550 次、约 11 秒的固定轮询；
- 回退锁的结束、续租、重建与缓存失效均使用 2 秒操作上限，防止 Redis 被配置为
  无读超时时让同步状态机永久卡在一次网络调用上；
- 首次 finalize 失败但缓存恢复成功时，在停止续租前用同一 token 再安全结束一次锁；
  Lua 令牌校验保证不会误删其他实例后来取得的锁；
- 超过额度回退锁保护窗口后继续失败关闭，并在鉴权与普通中继计费入口返回 HTTP 503，
  不再把同步超时标记为 HTTP 500；调用方自身取消或更早的 deadline 保持原始语义，
  不会被误分类为额度同步 503；
- Midjourney 保留本地额度读取错误的内部 HTTP 状态；额度同步超时返回 503，
  其他既有请求错误仍返回 400，分组负载饱和仍返回 429；
- 视频和其他异步任务的预扣费错误保留 `NewAPIError` 的本地错误与 `SkipRetry` 语义；
  额度同步 503 不跨渠道重试，也不记录为渠道故障或触发渠道禁用；
- Realtime WebSocket 的额度同步或本地预留写入失败会发送标准 `error` 事件并以 1013 关闭，
  额度不足会以策略错误关闭；所有预留错误都会终止连接并保留 `SkipRetry`，不再只记录日志后
  静默继续。每次成功片段按累计 usage 扩充同一个 `BillingSession` 的预留额度，命中信任额度
  旁路的长连接会在首个 usage 到达时退出旁路并开始累计预留，避免断开时一次性透支。
  最终结算只调整实际总额与累计预留的差额；usage 仅在预留成功后计入累计值，失败片段不会
  重复累计，错误结束时已成功片段仍会记录和结算一次，不会再次全额扣费。统一计费会话和
  兼容路径都先预留令牌再扣资金。非批量模式的资金失败使用唯一操作键持久补偿令牌；
  批量模式持有令牌刷盘锁，资金失败会在同一队列内原地抵消。令牌失败不会先扣钱包；
  持久补偿失败会保留在返回错误链和待处理记录中，由后续结算或 Worker 用同一键安全重放。
  任一 WebSocket 方向结束后先中断并等待两个读协程退出，再读取累计
  usage 和执行尾部预留，避免预留与结算并发；
- 手工渠道测试传递原请求 Context；Canvas、Playground、订阅、计费、分组、模型列表、
  用户模型和定价入口复用鉴权已写入的额度、分组或用户设置，不再重复读取完整用户缓存
  或重复执行订阅过期事务；
- 已返回 202 的 Canvas 与令牌 API 异步图片任务，若后台在调用上游前遇到本地额度同步 503，
  会分别延迟 1 秒、2 秒进行最多两次额外尝试，不再立即写入失败终态；
- 额度同步重试复用首次模型请求限流准入，不重复消耗总请求次数；只有最终真实成功才记录
  一次成功次数。客户端错误替换即使把内部 503 改成 200 或 302，也不会绕过内部重试、
  误记限流成功或把持续失败任务标记为 `SUCCESS`。

## 为什么同步可能超过 10 秒

`userQuotaFallbackLockExpiration=10s` 是分布式保护锁的单次租期，不是同步任务的总时限。
只要本地仍有待落库额度，后台会按租期续租；数据库写入失败、Redis finalize 失败或缓存失效
结果不确定时，保护状态会继续存在，直到待落库增量安全提交并清理缓存。因此真实基础设施故障
下同步可以超过 10 秒，这是防止旧额度被继续使用的安全行为。

本次优化将普通刷盘与真实恢复故障分开：普通刷盘期间继续使用可信 Redis 实时额度，不影响用户；
只有缺少可信额度或恢复状态未确认时才等待，单个请求最多等待约 11 秒后返回可重试的 503。
后台恢复继续运行，不会用解除保护或读取旧数据库额度来换取表面成功。

异步图片提交接口已经先返回 202，后台最多执行三次额度同步尝试；持续故障时，三次约 11 秒等待
加 1 秒、2 秒退避，最坏约 36 秒后写入失败终态。这个时长不会阻塞提交请求，也不会在已经
调用上游后重放生成请求。

## 安全与兼容边界

- 不读取、不返回可能过期的数据库额度；
- 不取消 generation 栅栏、跨实例回退锁或本地持久化保护；
- 不自动重放已经发往上游的请求。额度检查发生在上游调用前，因此等待重读不会造成重复生成或重复扣费；
- 异步图片可重试标记只在 `PreConsumeBilling` 返回 `ErrUserQuotaCacheSync` 且内部状态为 503 时写入，
  此时尚未调用上游；执行器依据该内部标记重试，不依赖客户端替换后的 HTTP 状态。普通上游 503、
  已经调用上游或已写出真实 2xx 的响应以及其他本地错误均不重试。每次尝试重建请求级上下文键，
  但复用首次模型限流准入，避免复用上一轮渠道、计费、响应状态或重复消耗限流次数；
- API 请求与成功响应结构不变；仅长期同步异常的最终状态码由 500 调整为 503；
- 上游渠道真实返回的 5xx 仍按既有策略重试和归责，本地额度同步错误不会影响渠道健康状态；
- 无数据库结构变更，SQLite、MySQL 和 PostgreSQL 行为一致。

## 验证

- 普通刷盘 `inProgress` 期间，可信 Redis 快照保持可读；无可信额度时数据库回退仍被阻断；
- 同步错误连续出现后恢复时，读取自动重试并返回最新额度；
- 请求上下文取消时立即退出；
- 同步超过等待窗口时仍返回 `ErrUserQuotaCacheSync`，保持失败关闭；
- 仅带 `ErrUserQuotaCacheSync` 标记的内部等待 deadline 映射为 503；普通 Redis、数据库和订阅
  事务超时保持原始分类，调用方自身取消或更早 deadline 不被改写；
- 130ms 远端锁等待最多探测 4 次；同用户 16 个并发探测合并为 1 次；
- 回退锁结束、续租、重建与缓存失效均验证遵守已取消的 Context；首次 finalize 失败后会在
  缓存恢复成功、停止续租前再执行一次 token-safe finish；
- 写侧 fallback busy 只尝试一次并立即进入数据库回退，不再固定轮询约 11 秒；
- 视频等通用异步任务的额度同步 503 不跨渠道重试、不归责渠道，原始错误链和 `SkipRetry` 标记保持可识别；
- 异步任务真实上游 5xx 仍会重试并归责渠道；
- Realtime 同步失败和普通预留写入失败均对客户端发送明确错误并终止连接，失败 usage 不重复累计；
  钱包和令牌余额级测试确认 trusted 长连接转入累计预留后，最终结算只扣除一次实际额度；
  统一计费和兼容路径的令牌更新失败都不会先扣钱包；非批量资金失败后的令牌补偿错误保持
  可见，相同补偿键重放不会重复增加额度；批量资金失败不会让令牌扣减越过刷盘锁；
  任一方向关闭时会等待两个读协程退出，尾部 usage 只预留一次且不会与片段预留并发；
- 手工渠道测试取消可传播；Canvas、Playground、订阅、计费、分组、模型列表、用户模型和
  定价入口优先复用鉴权上下文，可信快照存在时不再二次读取完整缓存；
- Midjourney 额度同步错误返回 503，既有 400 与 429 状态保持不变；
- 异步图片任务在同步恢复后成功完成；普通上游 503 只执行一次；持续同步异常在三次总尝试后
  终态失败；客户端把内部 503 替换成 200 或 302 时仍重试且不会误标成功；
- 额度同步重试只占用一次总请求限流，替换后的错误 2xx 不计成功，最终真实成功只计一次；
- 即使残留同步标记，已经写出的 2xx 响应也不会触发重放；
- 执行相关 Go 单元测试、格式化、`git diff --check`。

## 回滚

本变更无数据迁移。代码回滚后额度一致性保护仍存在，但短暂同步窗口会再次直接影响用户请求并返回 500。
