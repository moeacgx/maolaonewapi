# 流内 500 重试与失败亲和淘汰

日期：2026-08-04

## 问题

上游可能先以 HTTP 200 建立 SSE，再把普通 500 错误放在首个 `data` 帧中。流扫描器在处理
该帧前会设置首包时间并增加 `ReceivedResponseCount`，旧重试逻辑因此把“已读到上游错误”
误判为“已写给客户端”，直接返回 `no_retry_after_stream_started`。管理员已配置 500 可重试
也无法切换渠道。

客户端重新发起请求时，渠道亲和缓存仍指向失败渠道。流式错误的 HTTP 状态还可能保持 200，
Distributor 在请求结束后会把失败渠道再次记录为成功亲和绑定，造成连续重连仍粘在同一渠道。

## 修复方案

### 下游提交边界

- 正常 Gin 请求只以 `c.Writer.Written()` 判断下游是否已经开始；
- 仅设置 SSE 响应头、记录首包时间或增加接收计数都不算提交；
- Writer 不可用时才回退到 `SendResponseCount`，不使用上游接收计数；
- 未提交流内 500 按现有 `AutomaticRetryStatusCodes` 和重试预算执行；
- 任意数据或 Ping 已写出后仍禁止透明换渠，避免把两个渠道拼成一条 SSE。

任何实际发生的未提交流重试都会清理上一尝试的 SSE 响应头与敏感词延迟缓冲，不再只处理
容量错误。非流式上游 500 同样不会因首包计时而被误拦。

### 亲和绑定淘汰

只有本次请求实际采用亲和缓存绑定，且错误按现有策略可重试时，才尝试淘汰绑定。请求取消、
指定渠道、`skip_retry`、亲和规则配置 `skip_retry_on_failure`、预算耗尽和未配置重试的状态码
都不触发淘汰。

命中快照保存缓存键、渠道 ID、多 Key 索引和绑定修订号。删除时再次比较完整绑定：

- Redis 通过 Lua 原子执行 `GET`、完整值比较和 `UNLINK`；
- 内存缓存的比较删除与成功写回共用同键分片锁；
- 每次成功写回生成新修订号，即使并发请求写回相同渠道和相同 Key，旧失败请求也不会删除
  新绑定；
- `RelayInfo.LastError` 非空时禁止 Distributor 把 HTTP 200 失败流重新记录为成功绑定。

旧缓存记录没有修订号仍可读取；后续成功请求写回时会自动补充修订号，不需要数据库迁移或
人工清缓存。

## 安全与兼容边界

- 不修改数据库结构、模型定价、倍率或计费表达式；
- 不改变重试次数、状态码范围、渠道优先级、权重和跨分组策略；
- 不对已经向客户端写出的连接执行跨渠道重放；
- 只删除实际命中的精确绑定，不删除仅匹配到亲和规则但未采用的缓存；
- 多 Key 绑定必须同时匹配渠道和 Key 索引；
- `switch_on_success=true` 时，同一请求换渠成功后绑定最终成功渠道；关闭该配置时继续保留
  “成功重试后仍绑定初始渠道”的既有语义；
- 本次只修改本地源码和测试，不操作生产容器、数据库或 Redis。

## 验证

自动化测试覆盖：

- 真实 OpenAI SSE 首个错误帧已增加接收计数但 Writer 未提交，仍返回
  `status_code_retry`；
- 非流式首包计时、只设置 SSE 头和敏感词缓冲不阻断重试；
- Writer 已写出以及无 Writer 的保守回退边界；
- 请求取消、指定渠道、显式跳过、亲和跳过、不可重试状态和预算耗尽不淘汰；
- 实际命中删除、渠道不匹配、多 Key 索引不匹配、未命中不删除；
- 并发替换为其他渠道或同渠道新修订号时保留新绑定；
- 失败流不会在请求结束后重新写回亲和缓存。

验证命令均设置 60 秒超时；最终结果以交付说明为准。

## 回滚

本次没有数据库迁移。回滚后首个流内 500 会再次被接收计数误判为已提交流，失败亲和绑定也
会保留到 TTL 到期，并可能被 HTTP 200 失败流刷新。回滚代码无需处理缓存格式，带修订号的
JSON 绑定可由旧结构忽略未知字段。
