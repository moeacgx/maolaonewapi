# 渠道监控自动恢复探测

**日期**：2026-08-06
**类型**：bugfix

## 问题

渠道监控的“成功时自动启用”只在定时的“测试所有渠道”链路中累计连续成功次数。
普通请求和跨渠道重试继续使用普通渠道选择逻辑。

多 Key 渠道的普通选择器只允许使用状态为启用的 Key。当同一渠道的所有 Key 都因上游
错误被自动禁用时，渠道状态会变为自动禁用，但后续监控仍然无法选择任何 Key，直接得到
`no enabled keys`，因此没有机会验证上游是否已经恢复，连续成功次数也不会增长。

## 根因

渠道内多个 Key 是同一渠道的凭据池，不等同于用户 API 令牌。普通请求在多 Key 渠道内
可以先换用另一个启用 Key；根据错误类型和重试配置，后续才可能排除当前渠道并切换到
其他渠道。普通选择器不能放宽为使用已禁用 Key，否则会把明确淘汰的凭据重新用于业务流量。

系统监控会读取 Root 用户信息来构造内部测试请求和计费上下文，但不会遍历或验证用户
API 令牌；实际访问上游时使用的是被测渠道的 Key。

## 修改范围

- 新增仅供监控使用的 Key 选择入口。
- 普通请求、渠道重试和任务重试继续使用 `GetNextEnabledKey`，不探测已禁用 Key。
- 监控正常优先选择启用 Key；只有多 Key 渠道没有任何启用 Key 时，才从自动禁用 Key
  中选择一个恢复探测。
- 手动禁用的 Key 不参与恢复探测。
- 探测成功后按监控上下文中的多 Key 索引恢复本次实际探测的 Key；即使配置中存在重复
  Key 字符串，也不会误恢复其他索引。恢复前同时校验实际 Key，配置在测试期间发生变化
  时放弃本轮恢复。
- 普通选择与恢复扫描之间若发生并发状态变化，会重新选择一次，避免把已经恢复的渠道
  误记为本轮失败。
- 渠道测试的本地准备错误视为失败，只更新监控计数，不触发渠道自动禁用，也不允许
  自动启用。

## 行为契约

自动恢复仍要求：

- 渠道状态是自动禁用，而不是手动禁用；
- 自动监控和成功自动启用的有效策略均为开启；自动禁用开关不参与恢复判定；
- 渠道 `auto_ban` 开启且运行节点是 Master；
- 探测结果无错误，并达到全局或单渠道连续成功阈值。

## 安全与兼容性

- 不改变普通流量的 Key 禁用、同渠道 Key 故障转移和跨渠道重试规则。
- 不探测或恢复手动禁用的 Key。
- 不新增数据库字段或迁移，SQLite、MySQL 和 PostgreSQL 行为不变。
- 不记录或输出渠道 Key 内容。

## 测试

- 覆盖有启用 Key 时监控仍优先使用启用 Key。
- 覆盖所有 Key 自动禁用时可以选择恢复探测 Key。
- 覆盖所有 Key 手动禁用时仍拒绝探测。
- 覆盖监控上下文的并发许可在 Key 选择失败时释放。
- 覆盖本地测试错误不会被误算为成功。
- 覆盖重复 Key 字符串时按实际探测索引恢复。
- 覆盖 Key 配置在探测期间变化时拒绝使用陈旧索引恢复。

验证命令：

```powershell
go test ./model ./middleware ./controller ./service -count=1 -timeout 60s
go test ./... -run '^$' -count=1 -timeout 60s
go vet ./model ./middleware ./controller ./service
git diff --check
```

## 回滚

回滚监控专用选择入口即可恢复原行为；普通请求选择器和数据库结构无需回滚。
