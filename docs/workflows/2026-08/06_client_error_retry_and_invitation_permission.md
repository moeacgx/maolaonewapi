# 客户端错误替换、403 重试与邀请权限修复

## 问题与目标

- 运营需要按状态码与包含、精确或正则文案规则，把最终返回给客户端的错误状态码和文案
  一并替换；该能力不能改变上游错误识别、渠道自动禁用、重试、安全审计或内部日志。
- 管理员已经把 403 放入自动重试状态码时，渠道亲和的“失败后不重试”仍会提前终止，
  导致余额不足等渠道级 403 无法切换渠道。
- 注册路径只校验邀请码归属用户是否启用、是否被返利风控封禁，没有确认邀请人是否已经
  获得当前返利设置要求的邀请权限。

## 客户端错误响应替换契约

系统设置的“客户端错误消息”保存 `ErrorMessageReplacementRules` JSON 数组。每条规则包含：

- `matches`：匹配文本或正则表达式数组，数组内任意一项命中即视为该规则命中；
- `match`：兼容旧服务的首个匹配值，保存新格式时固定与 `matches[0]` 相同；
- `mode`：`contains`、`exact` 或 `regex`；
- `status_code`：可选，限定规则应用前准备返回给客户端的 HTTP 状态码；
- `replace`：命中后整体返回给客户端的文案；
- `replace_status_code`：可选，命中后返回给客户端的新 HTTP 状态码；未填写时保留原值。

规则最多 100 条，每条最多 64 个匹配值，按规则保存顺序匹配，首条命中后停止。同一规则
内的匹配值使用 OR 语义；`status_code` 与整组匹配值仍是 AND 语义。`regex` 使用 Go RE2
语法，保存时逐项编译；匹配值和替换文案均不能为空，单项最多 4096 个字符。两个状态码
字段填写时必须是 100 到 599 之间的整数。

旧配置只有 `match` 时，新服务自动把它读取为单个匹配值，无需数据库迁移。新页面保存时
同时写入 `matches` 和首个 `match`，保证滚动升级期间旧服务仍能读取同一规则。Default 与
Classic 提供等价的折叠规则编辑器；规则摘要展示匹配方式和匹配值数量，展开后可逐项新增、
修改或删除匹配值。输入框中按 Enter 添加下一项，Shift+Enter 保留值内换行。

`status_code` 与文案条件是“且”关系：填写 `status_code` 后，状态码和文案必须同时命中；
不填写时只匹配文案。状态码条件读取渠道状态码映射和内置容量规范化之后、运营规则应用
之前的客户端状态码。例如以下规则只会把包含 `Insufficient balance` 的 403 响应改为
429 和指定提示词，其他 403 或相同文案的 400 都不会命中：

```json
[
  {
    "status_code": 403,
    "match": "Insufficient balance",
    "matches": ["Insufficient balance", "account balance is insufficient"],
    "mode": "contains",
    "replace_status_code": 429,
    "replace": "渠道余额不足，请稍后重试"
  }
]
```

替换在 `NewAPIError` 序列化为 OpenAI、Claude 或 Realtime 客户端错误时基于独立副本执行，
包括响应已经提交后写入 SSE/Responses 流内的错误事件。每条规则同时匹配原始上游文案
和当前内置客户端文案，仍严格按规则保存顺序取首条命中，因此管理员规则可以覆盖容量
错误等内置稳定提示。请求 ID 也只追加到客户端副本；`Err`、`RelayError`、内部
`StatusCode`、`OriginalStatusCode`、错误码和内部消息视图保持原值，新状态码单独保存在
客户端响应视图。因此：

- `AutomaticDisableKeywords` 继续匹配上游原始错误；
- `AutomaticRetryStatusCodes` 继续按原始状态码决策；
- `cyber_policy` 和屏蔽词审计继续读取原始结构化错误；
- 渠道错误日志、自动禁用原因和模型广场失败统计不被替换文案污染。

普通 JSON 错误以及尚未提交响应头的流式请求可以同时替换 HTTP 状态码和提示词。SSE 或
WebSocket 已经开始传输后，HTTP 状态码或握手状态已经发送，协议上无法再次修改；此时仍
替换流内错误事件的提示词，但不会伪造一个已经无法生效的新 HTTP 状态码。Realtime 上游
`type=error` 帧没有对应的 HTTP 错误状态，只应用未填写 `status_code` 的文案规则；带状态码
条件的规则不会命中该帧。改写只修改 `error.message`，保留上游扩展字段。客户端状态码指标
记录实际写出的状态码，上游状态码与规范化状态码指标仍保留内部原值。

## 403 与渠道亲和重试

下游尚未提交响应、请求上下文仍有效、未指定固定渠道且仍有重试预算时，管理员明确配置
为可重试的 HTTP 状态码优先于渠道亲和的“失败后不重试”。重试判断同时检查渠道映射前
和映射后的状态码，因此默认范围中的 403 即使被渠道状态码映射改写，也会排除本次失败
渠道并进入其他候选渠道；对应精确亲和绑定也会被淘汰。多 Key 渠道同样必须排除，不能
继续在原渠道内换 Key；普通 429 和单 Key 故障仍保留既有的受控复用策略。

未配置为可重试的错误仍遵守亲和跳过策略。显式 `skip_retry`、已输出 SSE/Realtime 数据、
固定渠道、请求取消或超时、重试预算耗尽等边界不变。

## 邀请关系权限

密码注册和 OAuth 新用户创建在解析邀请码时，除账号启用和返利风控状态外，还必须通过
`AffiliateUserCanInvite`。公开注册开启时，无权限邀请码不阻止普通注册，但不会写入
`inviter_id`；邀请制注册开启且公开注册关闭时，无权限邀请码与无效邀请码一样拒绝注册。

创建用户的数据库事务内会锁定邀请人和邀请权限记录，并再次校验邀请码与邀请权限。权限在
前置校验后被撤销时，公开注册继续创建用户但把邀请人降级为零，不写邀请关系或邀请计数；
邀请制注册则终止创建。已有邀请关系不做追溯解绑。

## 验证计划

- 后端覆盖旧 `match` 兼容、`matches` 多值 OR、三种错误匹配模式、状态码与文案联合条件、
  首条优先、无效正则、空值、64 项边界和非法状态码拒绝；
- 覆盖普通 JSON 同时替换状态码与文案，已提交流内错误只替换文案，上游原始状态码与
  错误仍保持不变，并验证客户端序列化不会污染自动禁用原因和渠道错误日志；
- 覆盖 Realtime 上游错误帧文案替换、扩展字段保留，以及状态码条件在已升级连接上不命中；
- 覆盖渠道亲和开启时配置 403 仍重试并淘汰失败绑定；
- 覆盖多 Key 渠道收到 403 时仍排除整个渠道；
- 覆盖公开注册和邀请制注册中的未审批邀请人，以及事务内撤销权限；
- Default 执行类型检查、单元测试与生产构建，Classic 执行生产构建；
- 执行 `git diff --check`。

## 主分支集成

`custom-main` 与安全审计发布线存在重复补丁和独立提交。集成时以已经连续发版验证的安全
审计实现为准，同时保留主分支 Docker 手动重建说明。合并后删除了 Default 审计测试中
从旧主分支带回的越域 `view` 引用；该残留会让测试在执行初始化表达式时直接失败，不涉及
运行时代码或接口行为变化。集成树必须重新执行后端、双前端专项测试和生产构建。

## 兼容与回滚

本次不新增数据表或字段，配置仍存储在通用 Option 表，兼容 SQLite、MySQL 和 PostgreSQL。
清空 `ErrorMessageReplacementRules` 即可关闭客户端错误替换。旧后端会读取新格式同步保留的
首个 `match`，但回滚到旧前端后再次保存会丢弃第二项及之后的 `matches`，因此降级页面只应
用于只读或先完成配置备份。回滚邀请权限校验会重新允许未获权限用户建立邀请关系，不建议
单独回滚。回滚 403 优先级后，渠道亲和配置可能再次覆盖管理员的状态码重试范围。
