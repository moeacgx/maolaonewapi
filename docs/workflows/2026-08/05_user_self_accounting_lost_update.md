# 用户自助资料更新覆盖计费字段修复

## 背景与风险

用户自助设置接口会先读取完整 `users` 行，再通过 `User.Update` 写回资料。
当请求与计费结算并发时，旧快照中的 `quota`、`used_quota`、
`request_count` 可能覆盖计费链路已经完成的原子增减，造成余额或用量回滚。

同一类旧快照还可能在 Redis 用户缓存中覆盖实时维护的 `Quota` 字段。
因此只修改控制器调用点不足以形成完整防线，数据库和缓存都必须保护计费字段。

## 修复范围

- `PUT /api/user/self` 的侧边栏与语言偏好更新；
- `PUT /api/user/setting` 的通知及日志偏好更新；
- 订阅扣费偏好更新；
- `GET /api/user/token` 的管理访问令牌生成；
- 其他仍复用 `User.Update` 的身份绑定、资料和管理路径。
- 邀请注册增加邀请人数时的完整用户行 `Save`。
- `PUT /api/user/self` 的请求体与 `sidebar_modules` 输入边界。
- 用户绑定查询失败或目标已删除时的零行更新假成功。

## 实现约束

1. 设置、管理访问令牌、邀请码、邮箱、内置 OAuth 绑定、状态和角色均使用
   显式列更新，不再写回完整用户快照。
2. `User.Update` 采用资料字段白名单，只允许更新用户名、显示名和显式验证后的
   密码；计费、返利、令牌、设置、登录时间等字段不能从旧快照写回。
3. 多个设置入口通过 `setting` 旧值 CAS 重试合并并发修改，避免侧边栏、语言、
   通知与订阅扣费偏好互相覆盖。MySQL 文本 CAS 使用字节精确比较，不受默认
   不区分大小写排序规则影响。客户端重试与当前数据库值相同的设置时，仍会重试
   Redis 保额失效，避免上一次“写库成功、缓存失效失败”后的旧设置留存。
4. 管理员资料编辑按请求实际提供的字段构造更新，并以目标用户的旧角色作为 CAS
   守卫；角色与分组更新也检查旧值，未提供的字段不会被写回。
5. Redis 资料失效保留带有效 `Id` 标记的实时 `Quota`，数据库回填在读取前记录
   每用户 generation 并同步完成；同一用户 generation 冲突时重新读取，旧快照不得
   恢复已变更状态。generation 作为单调 fencing token 不设置 TTL，避免键过期后
   数值复用形成 ABA、让旧快照重新通过比较。
   只有 `Id` 与当前用户完全一致且 `Quota` 可按整数解析的完整 Hash 才允许原子增减；
   普通缓存未命中直接回填。读取时先解码 `Id`、`Quota`，再解码资料字段：错用户或
   `Id/Quota` 本身损坏时完整删除 Hash；`Role/Status/GroupId` 等资料字段缺失或损坏时
   保留已验证的实时额度，仅从数据库重建资料。读取命中仍要求 `UserBase` 全部字段均
   存在；只含可信 `Id+Quota` 的主动失效 Hash 也会保额重建，不能只在增量脚本中校验。
6. `PUT /api/user/self`、`PUT /api/user/setting`、`GET /api/user/token` 和
   `PUT /api/subscription/self/preference` 按认证用户 ID 限流，代理 IP 轮换不能
   绕过；Redis 路径使用单条 Lua 原子完成检查和写入。
7. `PUT /api/user/self` 请求体最大为 64 KiB，超限返回 413；`sidebar_modules`
   最大为 16 KiB，空字符串表示清除覆盖，非空值必须是 JSON 对象。
8. 批量额度缓存缺失时使用按用户跨实例回退锁，合并本实例已排队与正在刷新的增量后
   立即原子落库。额度调整显式分为两种语义：预扣和追加预留属于可中止操作，数据库
   失败时只恢复此前待落库增量并向调用方返回失败；上游已完成后的结算、补扣和退款
   属于已承诺操作，数据库失败时恢复“此前增量 + 本次增量”，进入受保护队列后按已
   接受处理，避免调用方重试非幂等变化或跳过后续用量与账单日志。
9. Lua 取得初始锁后先确认新租约，再替换并结束旧租约；新租约确认失败时继续保留旧
   租约和本地失败关闭标记。首次续租失败会记录错误并由后台继续恢复保护，但不能跳过
   本次数据库写入。Redis 响应错误且没有可确认令牌、回退锁持续忙或返回非法状态时，
   直接尝试原子落库并使缓存失效；落库仍失败时建立本地标记并持续争取分布式回退锁。
   Redis 已关闭、读取失败或调用方强制读取数据库额度时，必须同时检查本实例普通待刷盘
   增量、正在刷盘增量和回退标记；数据库读取前后都不能返回未包含这些增量的旧值。认证
   缓存若仍有可信 `Id+Quota`，可用该实时额度合并数据库资料并通过 generation 栅栏回填；
   普通待刷盘增量本身不能让资料更新后的部分 Hash 持续拒绝认证。
   fallback block 或 generation 冲突后必须丢弃此前捕获的绝对额度并重读，禁止把旧
   `preservedLiveQuota` 写入新 generation、覆盖并发事务已经提交的新额度。
10. 普通周期刷盘和事务内 `ConsumePendingUserQuotaDelta` 失败也会建立同一 Redis 保护，
    不能只把增量放回本实例内存。不同用户使用分片锁，单个用户的慢数据库写入不会阻塞
    全部额度请求。回退锁存在时禁止缓存快照回填，读取等待超时后失败关闭；后续落库
    成功才按唯一令牌释放，非持有者不能续期或完成回退。finalize 前先 Ensure 完整租期；
    finish/recover 阻塞期间续租协程只 Renew 现有锁，安全完成后再退出，避免锁提前过期，
    也避免完成后被旧协程重新建锁。持有者锁已过期且无人接管时会用同一令牌原子重建保护
    窗口；Redis 响应不确定时仍拒绝返回旧额度。锁完成与缓存失效同时失败时保留本地
    失败关闭标记，后续每次完成前先重新 Ensure 分布式保护再后台重试；数据库已提交、
    但未取得锁且缓存失效失败时也建立同样保护，不能在锁 TTL 过期后只保留单实例标记，
    也不能提前恢复读取。后台重试与同一用户的额度持久化共用互斥锁；旧标记被新的已承诺
    待落库增量复用时只维持租约，直到增量成功提交后才允许完成并删除标记。待落库增量
    净值为零时停止续租并释放锁。
    非批量路径仍先同步写数据库，成功后才异步更新 Redis。
    游戏余额兑换的数据库事务与随后缓存调整位于同一持久化保护窗口，不能在缓存同步前
    提前恢复认证读取；事务提交后若缓存调整结果不确定，必须建立 committed 失败关闭窗口，
    不能向客户端返回可重试错误。保护函数只能在同一用户的
    `ConsumePendingUserQuotaDelta` 回调内调用，不能绕过用户级互斥锁。部分 `Id+Quota` Hash
    无法读取 generation 时也必须失败关闭；批量计费启用时，任何数据库回退都必须完成
    generation 栅栏写入并重读 Redis，
    禁止返回无法确认是否遗漏本实例或其他实例后续 `HINCRBY` 的额度快照。
11. `FillUserById` 返回真实查询错误；要求用户存在的单列更新在影响 0 行时复核目标，
    不存在或已软删除时返回 `record not found`，不再向绑定接口报告假成功。
12. 邀请人数使用 `aff_count = aff_count + 1` 原子列更新，不保存邀请人的完整行。
13. 不变更数据库结构，SQLite、MySQL 和 PostgreSQL 均使用 GORM 列更新。

## 兼容性与安全边界

- API 请求与响应结构不变，现有前端不需要适配。
- 用户设置仍以完整 JSON 存储；并发修改会在有限次数内基于最新值重试，独立设置项
  会被合并，同一设置项仍以最后成功的 CAS 更新为准。
- 管理员额度调整继续走现有原子增减或显式覆盖接口，不通过 `User.Update`。
- 用户级关键操作限流沿用现有 `CRITICAL_RATE_LIMIT*` 配置；最大请求数为非正数时
  采用拒绝策略，不访问 Redis。
- 请求体上限与 `sidebar_modules` JSON 校验属于安全收紧；依赖超大或非 JSON 配置的
  非官方客户端会收到 413 或参数错误，需要改为正常配置对象。
- 本次只为管理员资料编辑增加目标旧角色 CAS，没有把所有管理员写操作改造成
  “事务内同时锁定并复核操作者与目标”。硬删除、认证绑定、Passkey、2FA 等管理入口
  的完整授权 TOCTOU 收口需作为独立工作项处理，不能把中间件中的角色快照视为事务守卫。
- 本修复不自动重算历史账务；历史差异需要依据消费日志另行审计和处置。
- 已承诺额度在批量模式下仍使用现有进程内队列；回退锁保证缓存不会读取旧值，但不会把
  队列变成跨进程持久账本。进程在数据库恢复和刷盘前异常退出仍可能丢失内存增量，长期
  需要独立的持久化账务流水或 outbox 解决。

## 验证计划

- 使用旧用户快照复现并发计费更新，确认资料保存后额度与计数保持新值；
- 验证设置单列更新只改变 `setting`；
- 验证相同设置值的重试仍会执行 Redis 保额失效；
- 验证访问令牌单列更新只改变 `access_token`；
- 验证管理员编辑的角色与分组 CAS、状态和角色显式列更新；
- 验证 Redis generation 冲突、部分 Hash 与实时额度保留；
- 验证缓存缺失、错用户 ID、损坏额度、回退锁忙、持有者续期、数据库失败恢复、
  首次续租失败仍精确写库一次、普通刷盘与事务合并失败进入保护、pending delta 成功
  落库后再释放、旧标记被新 pending 复用时后台只续租、新租约确认后再切换，以及
  不同用户互不阻塞；
- 验证预扣落库失败只恢复旧增量并返回失败，已完成结算和退款则恢复本次增量、按已接受
  返回并最终只落库一次；覆盖 Redis 错误无令牌、Redis 关闭、回退锁持续忙和非法状态；
- 验证控制器读取旧资料快照后插入计费原子更新，设置写入不会覆盖最新额度与计数；
- 验证部分 Hash 回填期间额度再次变化时，返回值来自 Lua 回填后的最新完整 Hash；
- 验证部分 Hash 无法取得 generation 时失败关闭，游戏兑换提交后缓存同步失败会进入保护；
- 使用真实 Redis 验证 generation fencing key 不过期、Lua 参数和锁令牌栅栏；
- 验证用户级限流不受客户端 IP 变化影响，非法最大请求数采用拒绝策略；
- 验证超大自助资料请求返回 413，畸形或超长侧边栏配置不写库；
- 验证不存在和软删除用户的查询、邮箱及 OAuth 单列更新返回失败；
- 运行 `go test ./model ./controller ./middleware ./router -count=1 -timeout 60s`、
  聚焦 `go vet`、`gofmt` 与 `git diff --check`。

## 回滚注意事项

本修复无数据库迁移。代码回滚会重新暴露旧快照覆盖计费字段的高危漏洞，
因此只能在用户资料写接口已由网关完全阻断时临时回滚。
