# 上游容量错误跨渠道重试

日期：2026-08-01

## 问题

OpenAI/Codex 的 Responses 接口在模型池满载时，可能以 HTTP 200 建立 SSE，随后通过
`error`、`response.error` 或 `response.failed` 事件返回：

```text
Selected model is at capacity. Please try a different model.
```

旧实现把原生 Responses 的失败事件当作普通终态，流处理器最终返回空 `usage` 和
`nil` 错误。外层因此按成功结算，使用日志出现输入、回复均为 0 的消费记录。Codex
渠道亲和规则默认还可以配置失败后不重试，使同一会话无法回落到其他渠道。

## 目标与范围

- 识别官方三种 Responses 流错误结构，以及 Chat Completions 流内错误对象，覆盖原生
  Responses、Responses 转 Chat 和 Chat 上游转 Responses 三条适配路径；
- 将容量失败统一归一为临时 429，并进入现有渠道重试链路（HTTP 200 仍保留原始状态码）；
- 对外统一返回描述“已触发OpenAI官方限流”；
- 容量错误可以绕过渠道亲和的“失败后不重试”，并排除当前渠道；
- 多 Key 渠道发生容量错误时同样切换其他渠道，不在原模型池内重复换 Key；
- 临时容量错误不触发渠道自动禁用；
- 最终失败写错误使用日志，不再写输入、回复均为 0 的消费日志；
- 保留请求取消、指定渠道、重试预算和已向客户端输出后不重试的既有边界。

## 错误识别契约

优先使用稳定错误码，包括 `account_pool_capacity_exhausted`、
`model_at_capacity`、`model_capacity_exhausted`、`model_overloaded` 和
`upstream_capacity_exhausted`。错误码精确匹配不依赖文案。

兼容官方当前只返回 `server_error` 的情况时，窄范围匹配
`Selected model is at capacity` 等已知文案。文案兜底只对 OpenAI、Claude、Gemini、
Rerank、Midjourney 或显式 upstream 错误类型生效，本地参数校验即使包含相同文字也不会
被误判为上游容量错误。

## 流式重试边界

流处理器不再暂存 `response.created`、`response.in_progress`、`role=assistant` 等前导
事件。每个合法上游事件都会立即进入下游发送和 `Flush` 流程，避免慢模型在首个正文
token 到达前没有任何响应字节，进而被客户端或反向代理按首字节超时主动取消。

透明重试边界因此收窄为：

1. 容量错误就是上游首个事件，且 Gin Writer 尚未提交时，可以清理未提交的 SSE 头并
   切换渠道；
2. 任意生命周期帧、角色帧、正文、推理、工具调用或 Ping 已经实际写出后，不再跨渠道
   重放；
3. 已提交流后收到容量错误时，在当前 SSE 中发送规范化终态错误，避免把两个渠道的响应
   拼接成一条流。

同一提交边界也用于普通流内错误。扫描器读到首个 SSE 500 时会增加上游接收计数，但只要
Gin Writer 尚未真正写出或刷新，该错误仍进入管理员配置的状态码重试范围。非流式请求收到
上游 500 响应头也不会因为首包计时已经开始而误判为“已向客户端输出”。只有 Writer 不可用
的内部调用才回退到 `SendResponseCount` 进行保守判断。

这个取舍优先保证流的持续可见性和协议完整性。容量错误发生在前导生命周期帧之后时，
虽然不再透明换渠，但客户端不会因长时间收不到首字节而误判连接中断。仍未产生任何事件的
即时容量错误继续保留跨渠道回落能力。

响应敏感词过滤仍以 Gin Writer 的实际提交状态为准。如果第一个实际输出尚在敏感词延迟
缓冲中，Writer 未提交，随后发生容量错误时仍可重试；但此前已经发送生命周期帧或角色帧
时，不能因为后续正文仍在过滤缓冲中而重新换渠。

流扫描器会预先设置 SSE 响应头。容量重试前同时清理未提交的事件流响应头和响应敏感词
延迟缓冲，使下一渠道可以重新决定响应类型，也不会混入上一渠道尚未下发的数据。最终
无法重试且响应未提交时，网关清理 SSE 头并返回 JSON 429。

该清理不再限定容量错误：任何尚未提交且实际进入跨渠道重试的流错误，都会丢弃上一渠道的
SSE 头和敏感词延迟缓冲，避免普通 500 重试时拼接两个渠道的数据。

Ping 与数据写入共用写锁。数据处理器在释放写锁前发布终态停止信号，已经等待写锁的
Ping 取得锁后会重新检查停止状态并放弃写入，避免错误判断完成后才由 Ping 提交响应，
导致外层既不能重试也不能返回 JSON 429。

客户端已经收到任意 SSE 事件或 Ping 后不再跨渠道重放。Chat 协议发送一条标准错误块，
Responses 协议发送标准 `response.failed` 终态；两者都使用“已触发OpenAI官方限流”，
不再把上游英文容量文案直接暴露给客户端，也不会追加 `[DONE]` 或
`response.completed`。

Responses 失败事件的协议结构和展示文案是两个独立契约。网关可以按敏感信息遮罩、国际化
或运营规则替换 `response.error.message`，但必须保留 `type=response.failed`、
`response.status=failed` 和上游结构化 `response.error.code`（例如 `cyber_policy`）。
上游先发送顶层 `error`、随后发送正式 `response.failed` 时，优先采用正式失败终态；如果
上游直接断流，网关才根据已保存的错误和响应元数据补发标准 `response.failed`。不能把失败
统一改成顶层 `error`，因为 Codex 不把它视为 Responses 终态，读到 EOF 后会误报流提前
关闭；也不能伪造 `response.completed`，否则会把真实失败标记为成功。

## 日志、计费与渠道状态

适配器遇到失败事件后返回 `NewAPIError` 和空 usage，因此不会进入
`PostTextConsumeQuota`。如果后续渠道成功，只保留最终成功消费日志；如果所有渠道均
失败，沿用现有 `recordChannelErrorLog` 写一条最终错误日志并执行预扣费退款。

容量不足表示上游模型池的临时状态，不代表凭据或渠道配置失效。即使 429 位于管理员的
自动禁用状态码范围内，也不会因此自动封禁渠道；渠道失败指标仍按实际尝试记录。

## 兼容性与安全边界

- 不新增配置、接口、数据表或迁移，数据库兼容性不受影响；
- 不改变管理员配置的重试次数、渠道优先级、权重和分组顺序；
- 指定渠道请求仍不重试，请求取消或超时仍立即停止；
- 普通非容量错误不会绕过渠道亲和规则；
- 策略上可重试的失败会淘汰本次实际命中的亲和绑定；请求取消、指定渠道、显式跳过重试、
  亲和规则要求失败后不重试和未配置重试的状态码均不淘汰；
- HTTP 200 流错误映射后保留 `OriginalStatusCode=200`，供内部指标追溯；
- 错误响应继续经过现有敏感信息遮罩，不记录请求正文或渠道密钥。

## 验证

自动化测试覆盖：

- 官方三种 Responses 错误结构和缺失 `type` 的错误对象；
- 普通 Responses、Responses 转 Chat、Chat Completions 三条流路径；
- Chat 上游转 Responses 的容量错误、前导事件和已提交终态错误路径；
- Cyber 策略失败保留 `response.failed`、`status=failed` 和 `cyber_policy`，仅允许替换
  客户端可见文案；
- 顶层错误后继续收到官方 `response.failed` 时采用官方终态，直接 EOF 时补发标准失败
  终态；
- 首个事件就是容量错误时可安全重试；
- `response.created`、`role=assistant` 等首个前导事件在下一事件到达前已经刷新；
- 已有任意 SSE 事件后不重试，并向客户端保留规范化容量错误事件；
- 首个输出仍在敏感词延迟缓冲且此前没有事件时，继续允许重试；
- 容量错误处理期间排队等待写锁的 Ping 不会在终态后提交响应；
- 渠道亲和失败跳过开启时仍回落、指定渠道和预算耗尽仍不重试；
- 多 Key 容量错误排除当前渠道；
- 容量 429 不自动禁用渠道；
- 重试前清理响应过滤缓冲和未提交的 SSE 响应头；
- 本地错误正文恰好包含官方文案时不会误判。

执行命令均设置不超过 60 秒的超时；最终验证结果以本次交付说明为准。

## 回滚

本次没有持久化结构变化。回滚首帧立即下发会恢复前导事件暂存，并重新引入慢模型首字节
饥饿风险；回滚容量错误识别则会让 HTTP 200 中的 `response.failed` 再次被视为成功并可能
产生 0 用量消费日志。因此不要把流发送策略、容量错误识别和控制器重试拆成不一致版本。
