# 开发反思报告：订阅支付与加密货币到账可靠性

## 4. 修改内容

### 4.1 订阅支付界面

- Classic 和 Default 均增加 OKPay 订阅支付入口。
- 余额支付始终可选，并在购买成功后刷新余额和订阅信息。
- Classic 的 USDT 链列表从主弹窗移入二级弹窗；Default 保持统一链选择弹窗。
- 删除无平台手续费提示。
- 修复 Classic 开票场景只按套餐金额估算余额、漏算开票费的问题。

### 4.2 OKPay 回调兼容

- 同时支持 Form 与 JSON 回调。
- 优先按原始字段顺序验签，并兼容按字段名排序的网关版本。
- 使用 OKPay 需要的 JSON 成功或失败回执。
- 回调在新订单入口关闭后仍可处理存量订单。
- 允许可信的成功回调完成此前标记为失败或过期的订单。

### 4.3 严格网关快照

- `TopUp` 与 `SubscriptionOrder` 新增第三方订单号、网关金额和币种字段。
- 网关金额按 8 位小数的字符串保存，避免浮点序列化误差。
- 创建支付链接前先固化金额和币种，返回第三方订单号后再完成快照。
- 新订单回调必须同时匹配第三方订单号、金额和币种。
- 支持在缺少商户单号时按第三方订单号回查本地订单。
- 升级前已经创建且没有快照的存量订单保留验签兼容路径，避免部署导致在途订单全部失败。

### 4.4 BEPUSDT 与缓存

- 成功回调严格核对法币订单金额。
- 保持官方要求的 HTTP 200 与响应正文 `ok`。
- OKPay、BEPUSDT 首次完成充值后同步增加 Redis 配额缓存。
- 重复通知只返回幂等成功，不重复增加数据库额度、缓存或日志。

## 5. 遇到的错误

### 错误一：合法 OKPay 回调验签失败

**类型**：协议兼容
**严重程度**：严重

旧实现只解析表单并强制排序签名。最新版网关可能发送 JSON，并按原始字段顺序计算签名，导致合法通知被拒绝。

### 错误二：数据库已到账但页面余额未更新

**类型**：缓存一致性
**严重程度**：严重

OKPay 与 BEPUSDT 直接更新数据库额度，却没有同步 Redis 配额缓存。启用 Redis 时用户继续读取旧余额，表现为“没到账”。

### 错误三：迟到成功通知被订单状态拒绝

**类型**：支付状态机
**严重程度**：重要

拉起支付超时或网关先通知过期后，真实成功通知可能稍后到达。旧状态机只允许待支付订单完成，导致已付款订单无法入账。

### 错误四：前端依赖验证出现假失败

**类型**：本地依赖树
**严重程度**：次要

本机没有全局 Bun，使用 pnpm 回退后锁到了不兼容的 Semi UI 新版本。恢复 `bun.lock` 对应依赖后 Classic 构建正常。

### 错误五：快照补丁误命中金额预览函数

**类型**：补丁上下文
**严重程度**：重要

充值金额预览与真实下单函数包含相同局部代码片段，首次补丁将快照变量插入了预览函数，造成重复变量声明。通过发布前只读审查发现并修正。

## 6. 根本原因分析

- 支付协议实现只覆盖了单一示例，没有用官方真实回调样本验证完整 Handler。
- 数据库余额与 Redis 余额是双写模型，但加密货币充值没有复用统一的缓存同步步骤。
- 订单状态被当作最终事实，没有考虑支付网关通知乱序和网络延迟。
- 本地订单只保存法币金额，没有保存实际发送给网关的币种金额，无法进行严格复核。
- 前端验证没有一开始就固定使用项目声明的 Bun 锁文件。

## 7. 调试过程

1. 用官方 OKPay 示例签名分别计算原始顺序和排序结果，确认两者不同。
2. 对比 Form、JSON 回调解析结果以及最终 Handler 入账状态。
3. 追踪充值事务结束后的数据库与 Redis 更新路径。
4. 对失败、过期、成功和重复成功状态执行高重复次数回归。
5. 对照 Dujiao Next 的 `ProviderRef`、`AmountSent`、`CurrencySent` 和统一回调比较逻辑。
6. 增加 GORM 字段迁移、快照持久化、第三方订单号回查和严格拒绝测试。

## 8. 经验总结

- 支付回调必须验证签名、商户身份、业务订单、第三方订单、金额、币种和状态，缺一不可。
- 实际发送给网关的金额必须在下单时固化，不能在回调时用实时汇率重新计算。
- 数据库事务成功后仍需处理缓存一致性，并确保重复回调不会重复写缓存。
- 支付状态机应允许经过验签和金额复核的迟到成功，但不能允许成功状态回退。
- 数据库新增严格字段时，需要为部署前的在途订单设计明确兼容策略。
