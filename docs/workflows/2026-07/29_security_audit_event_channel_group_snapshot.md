# 安全审计事件渠道与分组快照

## 问题

安全审计事件原来只保存单个路由分组字段，没有保存实际渠道快照；Classic 页面也没有
展示已有分组字段。审核员无法从列表和详情确认事件由哪个渠道、哪个业务分组产生。

## 方案

- 事件新增 `channel_id`、`channel_name`，保存事件发生时实际选中的渠道。
- 继续使用 `group_id`、`group_name` 保存本次请求实际使用的路由分组。
- 新增 `channel_groups`，保存渠道当时绑定的业务分组 ID、稳定编码和显示名称快照。
- 响应、SSE、Realtime 响应和跨渠道重试使用最终产生事件的渠道上下文。
- 请求在选渠前阻断时不伪造渠道，页面显示“尚未分配”。
- 历史事件的新增字段保持零值兼容，页面显示“历史事件未记录”。
- Default 与 Classic 的事件列表和详情同步展示渠道、实际路由分组及渠道绑定分组。

数据库只通过 GORM 自动迁移新增普通列，字段类型兼容 SQLite、MySQL 和 PostgreSQL。
列表查询显式包含新增列，内部 JSON 存储列不直接序列化给前端。

## 安全与数据生命周期

渠道名称和分组名称均为事件发生时的不可变审计快照。后续重命名或删除渠道、分组不会
改写历史事件。快照不包含渠道密钥、上游地址、令牌密文或其他凭据，继续随事件保留期
统一清理。

## 验证

- 模型层覆盖渠道及多分组快照的创建、列表、详情读取和历史零值兼容。
- 服务层覆盖选渠前阻断、固定渠道、响应阶段及跨渠道重试后的最终渠道快照。
- 控制器覆盖列表 JSON 字段并断言内部存储列不泄露。
- Default 与 Classic 覆盖列表、详情、历史事件和未分配渠道显示。
- Go 的 `model`、`service`、`controller`、`middleware`、`relay/helper` 和
  `relay/channel/openai` 测试通过。
- Default 路由展示与统一审计测试、类型检查、六语同步和生产构建通过。
- Classic 安全审计专项测试、ESLint、Prettier、八语同步和生产构建通过。
- 固定 `tmp-local-v10101.db` 下的 `3000/3001` 启动、状态接口、首页、默认账号登录和
  演示数据接口验证通过；验证后已停止两个测试进程。
