# 官方风控范围累计与自更新资产修复

## 问题

官方风控已经支持选择全部渠道、指定渠道或指定分组，但窗口累计和自动禁用仍只按
用户、事件来源、错误码和时间过滤。切换作用范围后，旧的范围外事件可能继续参与阈值。
分组命中还使用渠道绑定的全部业务分组，无法表达“只对本次实际路由分组生效”。

安全审计测试版 `.18` 同时被发布为 GitHub Prerelease，且 GitHub Actions 因账户
Billing 限制未生成二进制。自更新接口使用 `/releases/latest`，所以最初看不到该版本；
改为正式 Release 后虽然能看到，但由于缺少 Linux 资产，一键更新仍会禁用。

## 方案

- 指定渠道按最终实际渠道 ID 匹配；指定分组按本次最终实际路由分组的稳定编码匹配。
- 官方风控事件新增 `group_code`。指定分组累计只查询该字段，升级前缺少稳定编码的
  历史事件不参与分组阈值，避免把旧用户分组或渠道绑定快照误当成实际路由分组。
- 用户窗口累计次数和自动禁用共用同一个当前作用范围查询；作用范围切换后，范围外
  历史事件不再计数。
- 保存启用的指定分组范围时，确认分组真实存在且处于启用状态，并规范化为稳定编码。
- 渠道绑定分组查询改成两次 GORM 主键查询，避免 MySQL 8 直接引用保留表名
  `groups`，同时保持配置顺序。
- 自更新发布必须是正式 Release，并上传对应 Linux amd64/arm64 二进制与
  `checksums-linux.txt`；缺失资产时不允许一键更新。
- 发布内嵌版本优先于镜像中残留的 `VERSION` 文件，避免只替换可执行文件后仍被识别为
  旧版本；显式 `VERSION` 环境变量继续保留最高优先级。

## 兼容性与安全边界

- `prompt_audit_events.group_code` 由 GORM 自动迁移，类型为普通 `varchar(64)`，兼容
  SQLite、MySQL 和 PostgreSQL。
- 旧事件字段默认空字符串，仍可在审计列表查看，但不会进入指定分组自动禁用累计。
- 范围外的结构化 `cyber_policy` 仍保留内容策略标记，继续从模型广场失败指标中排除；
  只是不写安全审计事件、不累计次数、不自动禁用用户。
- 管理员和 Root 仍不参与自动禁用。

## 验证

- 模型层覆盖全部、指定渠道、指定分组三种累计范围。
- 服务层覆盖实际路由分组命中、范围外历史事件不累计、达到阈值后才禁用普通用户。
- 保存接口覆盖未知或停用分组拒绝。
- 发布后通过 GitHub Release API 验证正式版本和资产名称，再通过 zzapi 检查更新接口
  验证版本可见且一键更新可用。
- 在 Linux 容器中执行发布二进制的 `--version`，确认输出与 Release 标签完全一致。
