# 异步图片失败使用日志补齐

## 问题

异步图片任务（`image`）与 Canvas 图片任务（`canvas_image`）在成功时会由正常结算链路写入消费日志，但失败状态与错误使用日志此前没有统一的生命周期：

- 已进入渠道 Relay 的最终错误，仅在 `ERROR_LOG_ENABLED=true` 且错误允许记录时写入；
- 选渠前失败、无可用渠道、参数校验失败、任务超时和后台异常只更新任务状态；
- 因此任务日志可以显示 `FAILURE`，常规使用日志却可能没有对应失败记录。

模型广场的失败排除规则只影响性能样本，不参与上述使用日志链路。

## 方案

异步图片任务以“成功将任务状态从非终态更新为 `FAILURE`”作为失败日志补偿点：

1. 后台内部 Relay 请求携带异步图片任务标记。
2. 内部 Relay 跳过普通错误日志入口，但把原始错误类型与错误码传给任务终态，由终态
   统一负责失败留痕。
3. 内部请求结束时，把模型、渠道、分组和上游请求 ID 等上下文同步回任务执行器。
4. 任务失败状态更新成功后，强制写入一条 `LogTypeError` 使用日志，不受
   `ERROR_LOG_ENABLED` 影响。
5. 终态任务不重复执行失败转换，CAS 未获胜的并发收尾者也不写日志。
6. 后台超时扫描同样只由赢得 CAS 的实例写日志，覆盖进程重启后的遗留任务。

这样可覆盖选渠前失败、上游失败、空响应、超时和后台 panic，同时避免同一失败出现两条日志。

## 日志契约

补写日志保留用户、用户名、令牌、模型、分组、渠道和请求 ID；`other` 额外包含：

- `is_task=true`
- `task_id`
- `task_platform`
- `task_action`
- `task_status=FAILURE`
- `request_path`
- `status_code`
- `error_type=async_image_task_error`
- `error_code=async_image_task_failed`
- `channel_id`

错误正文沿用 `status_code=<code>, <message>` 格式，并在入库前执行敏感信息遮蔽。失败日志只用于可观测性，配额仍由既有退款或结算链路处理。

请求提交时会从 JSON、`application/x-www-form-urlencoded` 或 multipart 表单提取模型名，
并把模型、用户名、令牌及请求 ID 保存到任务私有快照；因此即使进程重启后才由超时扫描
收尾，日志仍能保留关键归属字段，也不依赖运行时用户缓存。2xx 空正文属于
上游无效响应，错误日志状态码记为 502，避免出现“失败日志却显示 200”。

## 兼容性与安全边界

- 不新增数据库字段和迁移，SQLite、MySQL、PostgreSQL 行为一致。
- 不改变同步图片、文本请求或模型广场失败过滤语义。
- `ERROR_LOG_ENABLED` 仍控制普通同步请求；异步图片任务因为已经形成可查询任务，最终失败始终留痕。
- 客户端 IP 只在原有管理员或用户 IP 日志开关允许时写入，后台补写不会绕过隐私配置。
- 状态更新与日志库可能部署在不同数据库，无法组成跨库事务；日志写入失败会记录服务器错误，任务失败状态不回滚。

## 验证

- 上游 400 失败会生成一条包含状态码、模型、令牌、渠道、分组和任务 ID 的错误日志。
- 内部 Relay 不直接写错误日志，任务收尾只写一条。
- 成功任务仍只生成消费日志。
- 超时、空响应和后台异常会进入任务失败补偿路径。
- JSON、URL 编码表单和 multipart 表单都能提取并持久化模型名。
- `go test -count=1 -timeout 60s ./model ./service ./controller ./router` 通过。
- `go vet ./model ./service ./controller ./router` 和 `git diff --check` 通过。
