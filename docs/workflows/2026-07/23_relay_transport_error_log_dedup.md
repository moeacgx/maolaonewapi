# Relay 传输错误日志收敛

日期：2026-07-23

## 问题

上游 HTTP 请求尚未取得响应时，`http.Client.Do` 可能因客户端取消、入口超时、
DNS、TLS、代理或连接错误而失败。当前实现将这类传输错误统一映射为可重试的
内部 500，并在每次渠道尝试失败时写入一条用户错误日志。

当入口请求已经取消时，后续尝试继续复用已取消的 Context，会立即失败；同一个
逻辑请求因此可能在同一秒产生多条内容相同、渠道链逐步增长的错误日志。

生产现场在 2026-07-23 09:53-09:56（Asia/Shanghai）确认：269 次
`do request failed` 全部为 `context canceled`，实际来自 56 个入口请求，单请求最多
被放大到 16 次渠道尝试。同期未发现 DNS、TLS、连接超时、reset、OOM 或容器重启；
入口 Nginx 存在 `/v1/responses` 499，说明下游在等待期间先断开。

## 目标与范围

- 请求 Context 已取消或超时时立即停止渠道重试；
- 每个最终失败的同步 Relay 请求最多写一条用户错误日志；
- 客户端已取消的请求不写用户错误日志，也不触发渠道自动禁用；
- 已开始响应后的客户端断开只记录为 `client_cancelled` 和信息级运行日志；
- 已开始响应后的真实上游断流记录为 `stream_error`，不伪造新的 HTTP 500；
- HTTP 流已经提交后不再追加普通 JSON 错误体；
- 普通故障不重复选择已经尝试过的渠道；
- `auto` 或多分组切换不得突破全局 `RetryTimes + 1` 次尝试预算；
- 保留每次渠道失败的运行日志、自动禁用判断和渠道可观测性样本；
- 单 Key 渠道 429 会排除当前渠道并切换其它候选；多 Key 渠道继续允许同渠道内
  Key 故障转移和退避；
- 启用跨组重试时优先切换未尝试渠道，不在原渠道耗尽全局预算；
- 不改变管理员配置的 `RetryTimes` 数值和分组选择顺序。

## 方案

1. `shouldRetryWithReason` 在常规重试判断中检查入口请求 Context；Context 已结束时
   返回稳定的非重试原因，已开始流式响应仍保持更高优先级。
2. 将渠道故障处理拆为“每次尝试处理”和“最终用户错误日志记录”。每次尝试仍执行
   运行日志和适用的自动禁用；只有确定不再重试时才记录数据库错误日志。客户端取消
   只有在底层错误链确实包含该入口 Context 的终止原因时，才记为信息级运行日志，
   不落用户错误日志、不自动禁用渠道；与取消同时发生的真实网络错误不会被误吞。
   自动禁用任务在进入异步队列前固化错误原因，避免与错误响应脱敏改写发生数据竞争。
   流扫描器以第一个终止事件作为唯一归因：`client_gone` 先发生时，后续关闭响应体产生
   的已知关闭错误不会覆盖它；错误链与入口 Context 匹配时归为客户端取消，真实 reset
   即使与取消同时发生也仍保留为 `scanner_error`。渠道指标使用同一因果优先级，避免
   仅凭检查时刻的 Context 状态吞掉真实传输或流错误。
3. 最终错误日志保留完整 `use_channel`，并增加尝试次数，确保错误收敛后仍可追溯。
   若下一轮因候选耗尽而无法选渠，恢复最后一次真实渠道错误，不用派发错误覆盖它。
4. 内存缓存和数据库选择路径都把 `ExcludedChannelIDs` 作为硬约束；普通故障和
   单 Key 渠道的 429 把失败渠道加入排除集合。多 Key 渠道继续使用现有退避或
   Key 轮换；`auto` 跨组和显式多分组则把当前渠道加入排除集合，优先完成跨组
   故障转移。
5. 外层 Relay 使用独立的全局尝试序号计算剩余预算；分组内部可以调整优先级游标，
   但不能重置全局尝试次数。每个请求在开始时固定 `RetryTimes` 快照，运行期配置变化
   不会截断已建立的待收尾错误。
6. 最终错误响应在写入前检查入口取消因果和 Gin Writer 状态。入口取消不再生成内部
   500 响应；HTTP/SSE 已经提交时只保留运行日志和流状态，不再向流尾追加 JSON。

## 安全与兼容性

- 不向客户端或用户日志暴露上游 URL、API Key、代理凭据等原始传输错误；
- 非取消类原始错误继续只写服务器错误日志，并沿用现有敏感信息遮罩；
- 客户端取消不再作为渠道故障参与自动禁用；渠道指标仍记录为 `client_cancelled`；
- 不涉及数据库结构或数据库专属 SQL，兼容 SQLite、MySQL 和 PostgreSQL；
- 不改变成功请求、已开始流式响应请求和指定渠道请求的现有行为。

## 2026-07-24 生产修订

`.204` 虽然在 `http.Client.Do` 返回时识别出了入口 Context 已取消，但
`ErrOptionWithHideErrMsg` 随后用脱敏文案替换了底层错误。控制器因此无法再通过
`errors.Is` 识别 `context.Canceled`，仍会把该请求写成用户可见的 500 错误日志。

热修保留脱敏后的对外错误文案，同时单独保留只用于内部错误链判断的原始 cause。
客户端取消继续停止重试、跳过渠道禁用和错误日志落库；真实传输错误仍按原规则记录，
不会因取消竞态被误吞。

## 生产发布边界

- 生产 Compose 仍标记 `.184`，但 2026-07-23 现场 `/api/status` 与容器内二进制确认
  实际运行版本为 `.201`；这是容器内更新造成的元数据漂移。
- `.202` 以 `.201` 提交为唯一基线，只包含本工作流列出的修复、测试和文档文件。
- 部署时必须把 Compose 镜像正式更新为 `.202` 并按镜像摘要核验，不能继续依赖容器
  内覆盖；发布前拉取并记录官方 `.201` 镜像摘要，作为应用容器的首选回滚点。
