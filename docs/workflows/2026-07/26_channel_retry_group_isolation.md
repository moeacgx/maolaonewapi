# 多分组重试的当前分组选渠道约束

## 变更目标

保留多分组令牌按配置顺序重试到下一分组的能力，并确保每次选渠道都严格使用当前重试分组的渠道集合。

例如令牌顺序为 `Hack,Pro特价,CodexPro`：

1. 首次在 `Hack` 分组选渠道。
2. `Hack` 请求失败后，下一次尝试立即进入 `Pro特价`，不在 `Hack` 内更换另一渠道重试。
3. `Pro特价` 请求失败后，下一次尝试立即进入 `CodexPro`。
4. 进入后续分组时，只从配置了当前分组的渠道中选择。
5. 只配置 `CodexPro` 的渠道可以在第三阶段被调用，但在 `Hack` 或 `Pro特价` 阶段不得被调用。

## 问题与根因

多分组令牌的分组列表是有顺序的重试范围，不是要求渠道同时具备所有分组的交集条件。排查时必须同时记录“当前重试分组”和“实际渠道”：仅当渠道不属于当前重试分组时，才属于路由错误。

## 运行语义

- 单分组令牌：选渠道行为不变。
- 多分组令牌：按令牌中的分组顺序跨组重试，每个分组最多发起一次上游请求。
- 当前分组上游请求失败后，下一次尝试必须立即切换到下一个有效分组，不得在原分组换渠道继续尝试。
- 进入后续分组：候选渠道只需支持当前模型和当前分组，不要求同时支持前面的分组。
- 共享渠道可在多个阶段参与选择；单分组渠道只在该分组成为当前重试分组时参与。
- 当前分组没有可用渠道时，可在本次选择中跳过该组；一旦已发起上游请求，失败后必须消耗并移动到下一组。

## 实现范围

- 多分组和 `auto` 的分组顺序保持不变。
- 多分组的重试预算按可用分组数量计算，不再用单组的 `RetryTimes` 阻断后续分组。
- 选择渠道时将当前重试分组传入现有的内存缓存或数据库选渠道函数。
- 内存缓存和数据库路径都只从当前分组的模型能力集合中选择。
- 不新增接口、配置、数据表或迁移，兼容 SQLite、MySQL 和 PostgreSQL。

## 安全与兼容性

- 多分组的配置方式、顺序和跨组重试能力保留。
- `cross_group_retry` 字段和前端开关保留，不强制关闭。
- 不引入分组交集限制，避免破坏多分组按顺序回落的原有意义。

## 测试计划

1. 验证 `Hack` 阶段只选择配置 `Hack` 的渠道。
2. 验证 `Pro特价` 阶段只选择配置 `Pro特价` 的渠道。
3. 验证切换到 `CodexPro` 后，可以选择仅配置 `CodexPro` 的渠道。
4. 验证使用后续分组渠道时，返回的实际选中分组已更新为该后续分组。
5. 验证首组同时有多个可用渠道时，第一次上游失败后仍直接进入第二组。
6. 验证分组数量大于 `RetryTimes + 1` 时，后续分组仍能按顺序得到尝试。

## 验证结果

- 多分组当前分组定向测试通过：各阶段只选择对应分组的渠道。
- 切换到正价分组后，仅配置正价的渠道可用；返回的选中分组为正价。
- 显式多分组和开启跨组的 `auto` 顺序测试通过：`Hack` 失败后立即进入特价，特价失败后立即进入正价，不会在前一组换渠道再试。
- 跨组 relay 重试预算按分组数量计算；单分组和锁定原任务渠道仍使用站点 `RetryTimes`。
- `go test ./controller ./model ./middleware ./service -count=1 -timeout 60s` 通过。
- `go vet ./controller ./model ./middleware ./service` 通过。
- `git diff --check` 通过；工作区内的换行符提示来自无关的既有改动。
