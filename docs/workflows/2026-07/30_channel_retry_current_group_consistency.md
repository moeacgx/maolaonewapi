# 数据库选渠与渠道当前分组一致性

## 变更目标

确保数据库选渠路径不会因为 `abilities` 中残留的历史分组记录，把已经移出当前重试分组的
渠道重新选中。多分组重试仍按令牌配置顺序执行，但每次尝试只能使用当前实际绑定该分组的
渠道。

## 问题与根因

未启用内存渠道缓存时，模型选渠会查询 `abilities` 取得指定分组和模型的候选渠道。
`abilities` 是模型能力的兼容索引：渠道编辑、分组迁移或异常中断后，旧分组对应的能力记录
可能暂时残留，不能作为渠道当前分组归属的唯一依据。

修复前，数据库候选只校验能力记录中的分组、模型、启用状态和优先级，没有再次核对渠道的
当前分组绑定。因此，渠道从 `Codex-Basic` 移到 `Codex-Official` 后，只要旧的
`Codex-Basic` 能力记录仍存在，请求就可能在 `Codex-Basic` 重试阶段误选该渠道。

## 运行语义

- `abilities.group` 用于快速找到支持当前模型与分组的候选，不代表最终分组授权。
- 数据库候选进入权重选择前，必须核对结构化 `channel_groups` 当前绑定。启动迁移尚未完成时，
  旧记录可回退 `channels.group` 兼容镜像；回填成功后关联表成为唯一权威，绑定缺失采用拒绝策略。
- 渠道当前不属于本次重试分组时，即使 `abilities` 仍有对应记录，也必须跳过该渠道。
- 分组编码清理首尾空白后精确比较，`VIP` 与 `vip` 保持为两个不同分组；这样可抵消
  MySQL 默认不区分大小写排序规则对候选查询的影响。
- 渠道没有结构化绑定且 `channels.group` 也为空时采用拒绝策略，历史能力记录不能单独
  授权路由。
- 结构化分组加载会用当前绑定覆盖进程内的旧字符串镜像，内存缓存与数据库路径遵循同一
  分组边界。
- 回填完成状态与当前数据库实例绑定，并缓存结构化表就绪状态；数据库切换不会继承旧状态，
  请求热路径也不再重复执行表结构探测。
- MySQL 启动迁移会把 `abilities.group` 与分组标识列一并调整为 `utf8mb4_bin`，保证复合主键
  允许 `VIP` 与 `vip` 两条能力记录同时存在。SQLite 和 PostgreSQL 不执行该 MySQL 专用 DDL。
- 渠道亲和复用在数据库模式下也执行相同校验，不能通过历史亲和记录绕过当前绑定。

## 实现范围

- 在数据库优先级候选过滤阶段加入渠道当前分组校验，再进入并发检查和权重选择。
- 结构化绑定存在时以稳定分组 ID 关联到当前编码；仅在回填尚未成功时兼容旧字符串镜像。
- 数据库渠道亲和校验复用相同边界；结构化绑定加载时同步修正进程内兼容镜像。
- 不新增接口、配置或数据表，不改变多分组顺序、重试预算、渠道权重和优先级语义。
- MySQL 现有部署会在启动阶段执行分组标识列大小写敏感排序规则迁移，包括
  `abilities.group`；该 `ALTER TABLE ... MODIFY COLUMN` 可能持有表锁并阻塞能力表读写，大表
  升级前应预留维护窗口并确认数据库有足够临时空间。迁移失败会阻止启动继续完成，避免在
  大小写语义不一致时接收流量。
- 仅使用现有 GORM 查询结果，兼容 SQLite、MySQL 和 PostgreSQL。

## 安全与兼容性

当前渠道分组是路由作用范围的最终边界，历史能力索引只能缩小候选，不能扩大渠道可用范围。
该约束避免分组编辑后的陈旧索引或亲和记录绕过管理员配置，同时保留尚未建立结构化绑定、
但仍有有效字符串分组镜像的旧渠道，避免升级后直接使全部历史渠道不可用。

MySQL 5.7.8 及以上版本通过 `utf8mb4_bin` 保证分组编码精确匹配；SQLite 与 PostgreSQL 保持
现有列定义并由查询后的精确比较保证相同语义。MySQL 升级迁移属于启动流程的一部分，不是
管理员手工迁移；执行时间取决于 `abilities` 等相关表的数据量与数据库版本。建议生产升级前
备份数据库并在同版本副本演练，迁移期间不要并行启动多个新版本实例。

回滚代码会恢复信任历史能力记录的旧行为，因此不建议在仍有陈旧 `abilities` 数据时回滚。
如需回滚，应先通过渠道编辑或能力重建确认能力记录与渠道当前分组一致。

## 测试计划与结果

1. 构造当前仅属于 `regular`、但仍残留 `special` 能力记录的渠道。
2. 验证从 `special` 数据库选渠时不会返回该渠道。
3. 验证当前属于 `special,regular` 的共享渠道仍可被两个分组选择。
4. 验证仅属于 `regular` 的正常渠道仍可在 `regular` 分组被选择。
5. 构造结构化绑定为 `regular`、旧字符串镜像与能力记录仍为 `special` 的冲突数据，验证
   随机选渠和渠道亲和都拒绝 `special`。
6. 验证 `VIP` 与 `vip` 大小写隔离，以及空分组渠道采用拒绝策略。
7. 验证结构化分组加载覆盖旧字符串镜像，内存缓存不会重新引入旧分组。
8. 验证既有多分组重试行为、渠道排除、优先级和权重选择不回归。
