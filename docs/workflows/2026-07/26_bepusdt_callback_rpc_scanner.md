# BEpusdt EVM 扫描漏单修复记录

## 问题现象

NewAPI 的 BEpusdt 充值订单偶发或持续收不到成功回调，用户侧表现为链上已经付款但订单仍过期或未入账。

## 根因

- NewAPI 的回调解析、签名校验、幂等入账以及 `200 + ok` 响应均正常。
- BEpusdt 已识别成功的历史订单全部完成回调，没有成功订单卡在通知阶段。
- 故障期间 BSC 与 Polygon 的公共 RPC 持续拒绝扫描请求，错误包括限流、套餐限制、归档查询限制以及要求 `eth_getLogs` 必须指定合约地址。
- 上游扫描器只按 ERC-20 `Transfer` 事件主题过滤，没有按 USDT、USDC 合约地址过滤，导致节点需要返回整条链的 Transfer 日志；失败区块又立即入队重试，进一步形成请求风暴。

因此，漏单发生在“链上付款识别”阶段，BEpusdt 没有识别付款时不会向 NewAPI 发出成功回调。

## 修复范围

生产 BEpusdt 使用基于上游主分支构建的修复镜像，包含以下调整：

1. `eth_getLogs` 同时按网络内 USDT、USDC 合约地址和 `Transfer` 主题过滤。
2. EVM 历史回溯批次的默认入队间隔调整为 1 秒。
3. 区块读取或日志读取失败后等待 2 秒再重试，避免立即回队形成高频重试。
4. BSC 与 Polygon RPC 更换为已通过历史区块日志和批量区块读取验证的节点。

本次没有修改 NewAPI 回调接口、订单状态机、金额校验或入账逻辑，也没有提高订单回溯时间窗口。

## 生产变更与回滚

- 服务目录：`/home/docker/bepusdt`
- 容器：`bepusdt`
- 数据库：`data/sqlite.db`
- 修复版本：`v1.24.1-fdbecad-rpcfilter-20260726`
- 修复前镜像已保留独立回滚标签。
- 变更前 Compose 与 SQLite 备份：`backups/codex-20260725231924-rpcfilter`

回滚时必须同时恢复备份中的 Compose 配置和变更前 RPC 配置，再重建单个 `bepusdt` 服务；回滚后重新检查数据库完整性、本机 HTTP、外部网关和应用扫描日志。

## 验证结果

- BEpusdt 模型层与 EVM 扫描任务完整测试通过。
- 两个生产候选 RPC 的历史区块 `eth_getLogs`（带合约地址数组）与批量 `eth_getBlockByNumber` 实测通过。
- 新容器版本、镜像 ID、数据库完整性和本机 HTTP 健康检查通过，容器无重启。
- 新容器启动后 BSC 与 Polygon 持续输出区块扫描成功记录，成功率为 100%。
- 新容器日志未再出现旧节点的限流、套餐、归档权限或缺少合约地址错误。
- `bepusdt.sn.ink`、NewAPI 状态接口和 BEpusdt 回调路由均可从公网访问；未签名访问回调路由返回参数错误是预期安全行为。

## 已知限制与后续处理

- 公共 RPC 仍不等同于带 SLA 的专用节点，应持续观察限流和可用率；业务量增长时优先迁移到带独立密钥的生产 RPC。
- 历史已过期订单不会因为本次修复自动全部恢复。补单前必须取得订单号或链上交易哈希，逐笔核对链、币种、金额、收款地址和交易时间。
- 当前 NewAPI 没有保存 BEpusdt 的服务端订单 ID，也没有主动查单补偿任务，仍主要依赖网关回调。后续如增加主动补偿，需要新增明确的订单映射、幂等和审计设计。
- 临时扩大历史回溯窗口会显著增加 RPC 压力，且可能触发已过期订单补回；必须单独评估和确认，完成后恢复原窗口。
