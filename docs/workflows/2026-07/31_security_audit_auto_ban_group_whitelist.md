# 安全审计自动封禁分组白名单

## 问题

`cyber_policy` 自动封禁当前与官方风控审计作用范围共用同一套渠道或分组条件。Root
可以限定哪些事件写入审计，但无法在保留审计记录的同时，把可信业务分组排除在自动
封禁累计之外。

## 目标与配置契约

- 内置策略和完整安全审计配置新增
  `cyber_policy_auto_ban_exempt_group_codes`，类型为业务分组稳定编码数组。
- 默认值为空数组，升级后保持现有累计与封禁行为。
- 页面提供分组多选白名单；选项继续复用
  `GET /api/security-audit/builtin-policy/groups`，不使用用户分组名称、渠道标签或
  关键词组。
- 保存时去空、去重、排序并解析为规范编码；新增的未知、停用或非法分组拒绝保存，
  已保存引用后来失效时允许原样保留，并继续使用 `expected_version` 的 CAS 冲突保护。

## 运行语义

- 官方风控作用范围仍只决定哪些精确 `cyber_policy` 事件写入安全审计；白名单不改变
  事件识别、客户端响应或事件留存。
- 自动封禁仅统计已成功持久化、位于官方风控作用范围、且实际路由
  `group_code` 不在白名单中的事件。
- 白名单分组命中的当前事件不得触发自动封禁。其他非白名单分组在滚动窗口内达到阈值
  后，仍按原有角色和状态条件禁用普通用户。
- 运行时直接按保存时确认的稳定编码匹配，不再次依赖分组启用状态；分组后来停用时
  仍保持豁免，直到 Root 明确移出白名单。显式迁移分组编码期间，当前编码和有效历史
  别名视为同一分组，旧配置缓存也不能成为误封触发点。
- 事件列表的 `user_cyber_policy_count` 与自动封禁使用完全相同的白名单条件，避免页面
  累计次数与实际处置不一致。
- 配置白名单后，升级前缺少 `group_code` 的历史事件无法证明来自非白名单分组，因此
  不参与惩罚性累计，避免误封。空白名单时历史行为保持不变。
- 管理员与 Root 永不自动禁用；事件写入失败时仍不得执行封禁。

## 数据与兼容性

`prompt_audit_configs` 新增 TEXT 配置列，以 JSON 数组保存稳定分组编码。迁移由 GORM
完成，兼容 SQLite、MySQL 5.7.8+ 与 PostgreSQL 9.6+。旧记录的空字符串按空数组读取，
不需要破坏性数据迁移。分组仍被白名单引用时拒绝删除，Root 需先从白名单
移除该编码，避免留下悬空的安全配置。

管理员执行旧分组编码显式迁移时，官方风控分组范围与白名单在同一事务内通过 CAS
改写为数字编码，配置版本只递增一次。历史审计事件不改写发生时快照；累计查询会把
当前编码展开为当前编码与全部有效历史别名，保证迁移前后的作用范围和豁免连续。迁移
完成后立即失效安全审计配置缓存；当前事件的官方风控范围判断和白名单快速跳过也使用
同一别名解析。迁移失败时分组、配置和别名全部回滚。

## 实现结果

- 模型、完整配置 API 与内置策略 API 共用同一字段和 CAS 保存契约。
- 已保存白名单引用后来停用时，仍可保存阈值等其他策略；只有新增引用要求当前启用。
- 自动封禁与列表累计共用同一查询范围；白名单非空时同时排除白名单编码和缺少
  `group_code` 的历史事件。
- 当前事件来自白名单分组时仍成功写入审计，但不会触发自动处置；旧白名单编码与迁移后
  的新事件编码也按同一分组处理，分组身份解析失败时保持审计、跳过惩罚。
- 分组管理会阻止删除仍被白名单引用的分组；停用分组不会取消已经保存的豁免。
- Default 与 Classic 均提供多选、失效引用展示、加载失败重试和未保存变更检测。
- 页面明确提示白名单只能缩小自动封禁范围；若需覆盖全部非白名单分组，上方官方风控
  作用范围必须选择“全部渠道”。
