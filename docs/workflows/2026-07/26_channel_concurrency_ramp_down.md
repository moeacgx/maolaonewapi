# 渠道并发上限缓降工作记录

## 变更目标

管理员调低单个渠道或标签下渠道的并发上限时，避免配置保存后大量新请求瞬间切换到其他渠道；调高并发上限时保持原有的立即生效逻辑。

## 运行语义

- 有限上限调低时，以渠道当前在途请求数和新上限中的较大值作为缓降起点。
- 从 `0`（不限制）改为有限上限同样执行缓降；因此不限并发渠道也会在进程内记录在途请求数。
- 缓降持续时间最多一分钟，有效上限从起点线性收敛到新上限。
- 缓降期间不会取消或中断已经进入上游的请求；新请求只能在当前有效上限仍有余量时进入。
- 当前在途请求数不高于新上限时，无需缓降，直接使用新上限。
- 调高上限或改为 `0` 时立即生效，并取消尚未完成的缓降。
- 缓降期间再次调低时，从当时的在途请求数重新计算缓降起点。
- 在途请求归零后清理该渠道的运行时状态；后续请求直接按数据库中的当前配置初始化。

## 实现范围

- 缓降状态位于 `model/channel_concurrency.go`，与现有进程内并发占用计数共用同一互斥锁。
- 普通渠道编辑和标签批量编辑仍沿用原有数据库及缓存刷新流程；运行时在读取新渠道配置时识别上限变化。
- 不新增接口、配置项、数据表或数据库迁移，兼容 SQLite、MySQL 和 PostgreSQL。

## 安全与兼容性

- 并发许可的获取与释放契约保持不变，所有请求完成、失败和重试路径仍必须成对释放。
- 调高逻辑没有延迟；如果调高后的新上限仍低于当前在途请求数，只是不再接收新请求，不会中断在途请求。
- 单渠道并发及本次缓降状态仍是进程内状态。多实例部署不会形成严格的全局并发上限；如需全局限制，仍需带租约回收的 Redis 分布式信号量。

## 测试计划

1. 验证有限上限调低后从当前在途并发开始线性收敛，并在一分钟后严格使用新上限。
2. 验证 `0`（不限制）调为有限值时同样缓降。
3. 验证直接调高和缓降途中调高均立即生效。
4. 验证原有不限并发、并发占满、释放不为负数、候选渠道过滤及请求结束释放行为不回归。
5. 执行模型层、分发中间件和渠道测试的定向高重复测试，并执行 `go vet`、Markdown 格式及 `git diff --check`。

## 验证结果

- 缓降相关模型测试连续执行 50 次通过。
- 模型层、中间件和控制器并发定向测试连续执行 10 次通过。
- `go test ./model ./middleware ./controller -count=1 -timeout 60s` 通过。
- `go vet ./model ./middleware ./controller` 通过。
- Go、Markdown 格式检查和目标文件 `git diff --check` 通过。
