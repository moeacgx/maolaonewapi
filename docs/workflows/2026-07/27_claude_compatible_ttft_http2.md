# OpenAI/Codex 首字延迟排查与 Claude 方向排除

> 历史文件名沿用最初的 Claude Transport 假设；该假设经代码和生产数据核对后已排除。

## 问题与基线

用户反馈当前 OpenAI 类型渠道上的 Codex 模型首字延迟高，并要求与
`v1.0.0-rc.10.1.10.133` 对照。最初曾把问题关联到 Claude Code Transport 指纹，
但实际请求走的是 OpenAI `/v1/responses` 或 `/v1/chat/completions`，不会进入
Claude uTLS 分支。

对照范围：

- 基线：`v1.0.0-rc.10.1.10.133`。
- 生产实际运行程序：`v1.0.0-rc.10.1.10.213`。容器镜像引用仍显示 `.184`，但容器内
  `/new-api` 已被自更新覆盖，不能用镜像标签判断运行版本。
- 待发布代码：当前分支。

## 已确认结论

- OpenAI/Codex 请求不会调用 Claude Code uTLS Transport。
- 基线、生产版和当前版的普通 OpenAI 客户端都复用共享连接池并启用 HTTP/2。
- 默认连接池参数未发生可解释本次回归的变化。
- `.133`、`.184` 与 `.213` 都在流扫描器收到第一条非空 SSE `data:` 后记录首字，
  `Responses` 事件处理顺序的变化没有改变计时触发点；当前高值不是新版把首字定义得更晚。
- 当前所谓 TTFT 通常是 `response.created` 的到达时间，并非真正的首个文本 delta；这是
  所有对照版本共有的统计语义缺口，不能用来解释版本间回归。
- `.133` 会把请求体中的 `reasoning.effort=max` 归一为 `xhigh`；从 `.161` 起改为
  原样转发真正的 `max`，对应提交为 `24195ff32`。
- OpenAI 官方当前把 `max` 定义为合法但质量优先的最高推理力度，并明确提示更低力度
  有利于速度。因此旧版较低首字的一部分来源是隐式降低推理力度，不是 Transport 更快。
- `max` 的延迟影响由上游实现决定，不能把所有渠道统一回退为 `xhigh`；需要低延迟时应
  由调用方显式选择 `xhigh`，或只在已验证的兼容渠道上做条件映射。
- 因此不新增“Claude 低首字 HTTP/2”渠道开关，也不把 Claude 指纹作为本次修复。
- 现有 Claude Transport 行为保持不变。

官方参考：

- [Reasoning effort](https://developers.openai.com/api/docs/guides/reasoning#reasoning-effort)
- [GPT-5.6 模型参数迁移说明](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters)

## 生产只读核对

生产 `/api/status`、启动日志和 `/new-api --version` 共同确认当前运行 `.213`。近两天
OpenAI 类型的 Codex 请求显示：

- 同一模型在不同上游渠道的首字中位数差异可达数倍，渠道差异明显。
- 当前主要渠道均为 OpenAI 类型、原生 `/v1/responses`、单 Key，未配置代理、请求体透传、
  `responses_to_chat`、请求头覆盖或 reasoning/cache 参数覆盖。
- 每个上游都在复用一条 HTTP/2 连接；慢渠道未发现 GOAWAY、拒绝流、明显重传或发送队列
  堆积。最慢渠道的网络 RTT 虽比最快渠道高约 60 毫秒，但不足以解释数秒差异。
- 上下文经常达到 10～16 万 Token，且大多已有较高缓存命中。
- 7 月 27 日 09～10 时的缓存命中虽有小幅下降，但保持快速的渠道也有相同变化，不能解释
  慢渠道数秒级上升。

生产没有开启分段诊断，本次只读排查未修改环境变量、容器或数据库。

### `.203` 与 `.205` 生产边界

`.204` 的 17 分钟窗口不能作为“低首字版本”证据。渠道 323 的 169 条
`gpt-5.6-sol` Responses 请求中，167 条 `prompt_tokens=completion_tokens=0`，167 条
`response_count<=4`；166 个被记为成功的 attempt 中只有 1 个带 usage。大量请求经过
多次重试后仅收到 4 个 SSE 事件便 EOF，说明 `.203` 首次进入生产时破坏了部分 Responses
历史兼容。该版本随后回滚，其约 966 毫秒的表面中位数是坏流造成的假低值。

`.205` 首次随 `.209` 进入生产。以 `.199 -> .209` 切换前后各 44 分钟，固定渠道、令牌、
`prompt_cache_key` 指纹、effort 以及 prompt/cache Token 分桶配对：

- 渠道 256：28 个配对分层、53/57 个请求，首字中位数 `2475ms -> 2541ms`。
- 渠道 325：123 个配对分层、317/304 个请求，首字中位数 `1527ms -> 1575ms`。

同窗口缓存读取占比也没有坍塌：渠道 256 为 `84.04% -> 92.94%`，渠道 325 为
`94.09% -> 92.59%`。因此 `.205` 删除普通 OpenAI 请求的 `client_metadata` 没有形成
可解释当前数秒退化的回归台阶。

### 7 月 27 日上游时段退化

固定渠道、令牌、会话指纹、effort 和上下文分桶，将 7 月 26 日基线时段与 7 月 27 日
高延迟时段配对，多个 effort 在同一渠道同步变慢：

- 渠道 323：`high 888ms -> 1895ms`、`max 1591ms -> 4688ms`、
  `xhigh 1315ms -> 3926ms`。
- 渠道 325：`high 1104ms -> 3259ms`、`max 849ms -> 5074ms`、
  `xhigh 1084ms -> 1731ms`。

7 月 27 日 09～10 时，渠道 323、325 的小时首字中位数升至约 4.7～5.6 秒，新加入的
渠道 391 约 7.6 秒；同一时段渠道 267 仍约 1.3～1.5 秒。最近 3 小时按实际分组统计：

- `Codex-Pro`：渠道 267 约 1.8 秒，渠道 256 约 3.5 秒。
- `Codex-Hack`：渠道 323 约 4.4 秒，渠道 325 约 4.0 秒，渠道 391 约 9.8 秒。
- `codex-pro特价`：渠道 323 约 4.7 秒，渠道 325 约 5.1 秒，渠道 391 约 7.4 秒。

排查末一小时的 `gpt-5.6-sol` 首字 P50/P90 仍呈明显渠道分化：渠道 267 为
`1.388s/4.135s`，渠道 323 为 `4.635s/9.489s`，渠道 325 为
`4.743s/20.173s`。在 `.213` 不变的前提下，将 7 月 26 日和 27 日同一时段固定渠道、
令牌、effort、上下文和缓存分桶配对，渠道 325 的 `max` 从 `1.274s` 升至 `6.128s`，
渠道 256 同期却从 `5.698s` 降至 `3.522s`。相反方向的渠道变化排除了 NewAPI 公共路径
发生统一回归，更符合各上游账号池或推理队列的时变状态。

渠道绑定仍符合配置：256、267 只属于 `Codex-Pro`；323、325、391 属于
`Codex-Hack`、`codex-pro特价` 和 `Codex-Pro`。未发现请求落到未配置当前分组的渠道。

快速渠道也存在上游容量边界：最近 3 小时渠道 267 返回 70 次
`account_pool_capacity_exhausted`，主要集中在 09:33～09:58；渠道 256 有 3 次同类错误。
其他慢渠道在本地的估算平均并发明显低于配置上限，且流量下降时首字仍继续上升。证据
共同指向上游推理队列或账号池容量，而不是 NewAPI 本地并发锁排队。

## 推理力度版本分界证据

生产保留的启动日志显示，`2026-07-10 12:11:50 +08:00` 从 `.158` 切换到
`.161`。取切换前后各 5 小时 33 分钟的同长度窗口：

- 切换前 `gpt-5.6-sol` 只记录到被归一后的 `xhigh`，没有 `max`。
- 切换后 `max` 立即大量出现：历史渠道 172、178、222 分别记录 5955、4300、
  3735 个 `max` 流式样本。
- 同一时段不同历史渠道的 `max/xhigh` 差异方向并不完全一致，证明影响落在上游推理
  实现而非 NewAPI 公共连接池。

严格配对后，`.158 -> .161` 分界处的 `max` 影响呈明显渠道差异：历史渠道 222 的配对
中位数约增加 143 毫秒，渠道 172 反而下降，渠道 178 样本较少且上升。该语义变化能
解释旧版与新版的一部分观感，但远小于 7 月 27 日部分渠道数秒级的时段波动。
进一步固定同一用户后，`max/xhigh` 差异中位数仅约 38 毫秒；因此真实 `max` 是部分渠道
上的放大因素，不是本次整体数秒退化的主因。

当前 `codex-pro特价` 最近 3 小时的观察值仍显示部分上游对真实 `max` 更慢：渠道 323
约 `4.9s / 2.2s`（`max / xhigh`），渠道 325 约 `5.8s / 3.6s`；渠道 391 两者都在
约 7 秒。与此同时，`Codex-Hack` 的请求大多为 `xhigh`，首字仍达到约 4 秒。因此
`max` 是渠道相关的放大因素，不是当前整体高延迟的唯一原因。

还需注意，当前四个主要 OpenAI 渠道并不存在于 `.133` 的历史生产时段：渠道 256、
267、323、325 分别创建于 7 月 13 日、14 日、20 日、20 日。因此不能把历史生产的
`.133` 与当前生产直接视为“同渠道只换程序版本”的 A/B；当前上游组合本身也是重要
变量。源码差异可以证明出站推理力度改变，但若要测量某一渠道的净版本影响，仍需固定
同一个渠道、请求体和网络出口做受控对照。

若某个兼容上游需要恢复旧版行为，可在该渠道现有参数覆盖中显式配置，而不改变其他
渠道的标准语义：

```json
{
  "operations": [
    {
      "path": "reasoning.effort",
      "mode": "set",
      "value": "xhigh",
      "conditions": [
        {
          "path": "reasoning.effort",
          "mode": "full",
          "value": "max"
        }
      ]
    }
  ]
}
```

该配置会降低实际推理力度，必须作为渠道级兼容策略明确启用，不能作为全局默认值。

## 版本差异排除

以下变化已经真实进入过生产，不能再按镜像标签误判为“尚未运行”：

1. `.203` 清理 Responses 历史项中的 `id`、`status`、`namespace`，首次部署确实造成坏流，
   随后回滚并由 `.205` 的 Responses 兼容修复收敛。
2. `.205` 后普通 OpenAI 适配器删除 `client_metadata`，但严格生产边界没有对应 TTFT 台阶。

这不等于字段对所有兼容上游都永远无影响；但针对本次生产高延迟，已有同渠道严格配对
证据，不能再把它们列为主要根因。

`.133 -> .213` 的原生 OpenAI Responses 出站请求静态差异还包括 `.184` 新增保留
`prompt_cache_options`。现有生产日志不记录该字段是否出现，不能据此断言它参与了本次
回归；需要受控请求或仅记录“字段是否存在”的脱敏诊断才能排除。

## 渠道亲和行为差异

从 `.167` 起，Codex 亲和键会优先使用请求体中稳定的 `prompt_cache_key`。`.133` 会先
读取 `x-client-request-id`，导致即使请求体已有稳定缓存键，也可能按单次请求标识选渠。
旧行为弱化了会话粘性，新行为能保护上游提示缓存，但会让某次选中的慢渠道持续影响同一
会话。

生产当前启用渠道亲和，`default_ttl_seconds=360`、`switch_on_success=true`、
`skip_retry_on_failure=false`。最近 5 分钟绝大多数会话指纹只命中一个渠道。这会放大
“连续几轮都慢”的体感，但亲和命中仍会验证模型和当前分组，不会让渠道越过其分组绑定。
它也不是上游首字本身从 1 秒升到 5 秒的根因。

Redis 只读快照中共有 129 个有效亲和键，其中渠道 323 为 31 个、325 为 32 个、256 为
42 个；前三者平均剩余 TTL 分别约 260、237、261 秒。323/325 合计承载约 49% 的活跃
亲和键，因此上游变慢后，稳定亲和会让相当一部分会话在数分钟内持续命中慢渠道。

## 模型广场统计口径修复

另确认模型广场详情的旧性能采集仍用
`FirstResponseTime - StartTime` 计算 TTFT，会把本地预处理、前序失败尝试和重试等待
计入首字；请求日志和渠道观测已经使用最终上游尝试的
`FirstResponseLatencyMilliseconds()`。

该口径自模型性能采集引入时就存在，但 `.196` 增加韧性重试和同渠道 429 冷却后更容易
被放大：最终上游尝试本身可能只需 1～2 秒，模型广场却会把前序失败和冷却等待一起显示为
首字。它能解释模型广场与请求日志/渠道看板数值不一致，但不改变客户端真实经历的总等待。

本次将模型广场性能采集同步为最终上游尝试口径，并补充“整次请求 8 秒、最终尝试首字
500ms”的回归测试。总延迟仍保留整次请求耗时，不会掩盖重试对用户总体等待的影响。
修复只影响新采集样本，旧聚合数据不做危险的历史改写，会随展示窗口自然退出。

## 首 SSE 与真实首输出

`StreamScannerHandler` 在把事件交给 OpenAI Responses 解析器之前就调用
`SetFirstResponseTime()`。因此请求日志的 `frt`、渠道 TTFT 和本次修正后的模型广场 TTFT
都表示“首条非空 SSE”，常见首事件是 `response.created`。它们适合观察上游开始响应，
但不能等同于用户看到的首个文本。

后续若要展示严格的生成首字，应保留现有 `frt` 以维持历史可比性，并新增两个独立字段：

- 首个有效输出事件耗时，覆盖 reasoning、工具调用和文本输出。
- 首个 `response.output_text.delta` 耗时，仅用于实际产生文本的请求。

不能直接把现有 `frt` 改成文本 delta；纯工具调用或无文本响应会失去 TTFT，历史曲线也会
在升级点发生不可比较的语义跳变。

## 诊断方法

临时启用：

```text
UPSTREAM_TIMING_DIAGNOSTICS=true
```

日志中的关键字段：

- `before_do_request_ms`：上游调用前的本地转换和预处理。
- `got_conn_ms`、`wrote_request_ms`：连接获取与请求发送。
- `got_first_response_byte_ms`：网络、连接和上游响应头耗时。
- `first_sse_data_ms`：收到首个有效 SSE 数据。
- `first_downstream_write_ms`：首次写给客户端。

诊断日志不得记录渠道密钥、请求体、用户令牌或完整会话标识。生产启用该环境变量需要
重启容器，必须单独获得确认。

## 验证计划

- 对同一真实请求分别运行 `.133` 与当前版。
- 固定渠道、模型、请求体、客户端请求头和网络出口。
- 比较实际出站 URL、非敏感请求头、请求体字段集合与请求体大小。
- 比较连接获取、响应头、首个 SSE 和首次下游写出四段耗时。
- 另行比较首个有效输出事件与首个文本 delta，不能继续用首 SSE 代替真实首字。
- 分别验证保留 `client_metadata` 与跳过历史清理是否改变首字。
- 分别验证保留或删除 `prompt_cache_options` 是否改变缓存写入和首字。
- 固定同一 `prompt_cache_key`，比较亲和开启与关闭时的渠道分布、缓存命中和用户端总等待。
- 只有复现出稳定差异后才修改 OpenAI/Codex 逻辑。

## 本次处理

已撤销尚未提交的 Claude 低首字开关及两套前端入口。此次排查保留现有通用分段诊断能力，
修正模型广场 TTFT 的重试计时口径；未改变生产环境，也未把渠道相关的 `max → xhigh`
映射写成全局默认修复。
