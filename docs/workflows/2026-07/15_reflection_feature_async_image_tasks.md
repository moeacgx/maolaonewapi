## 1. 概述

为 Canvas 与普通令牌 API 增加统一的异步图片任务能力，并提供默认一小时的图片结果数据保留策略。清理任务只清空到期图片正文，保留任务状态、计费与审计字段，同时补齐任务日志中的轻量图片预览。

## 2. 修改内容

### 修改的文件

- `controller/`、`router/`：增加 `/v1/images/tasks` 提交、查询与内容读取路径。
- `model/`、`service/`、`constant/`：区分 `canvas_image` 与 `image` 平台，增加分批清理任务。
- `setting/`、`common/`：增加图片任务数据保留时间及运行时同步。
- `web/default/`、`web/classic/`：增加性能设置、任务日志图片预览和多语言文案。
- 对应测试文件：覆盖保留时间校验、清理边界、平台隔离、路由注册及图片内容安全。

### 主要变更

- 新增 `POST /v1/images/tasks`，通过 `action` 支持生成与编辑。
- 新增通用任务查询和图片内容读取端点。
- 默认保留图片结果一小时，`0` 可关闭清理，最大值为 8760 小时。
- 仅主节点每分钟分批清理 50 条到期结果，保留任务记录。
- 清理同时覆盖 `canvas_image` 和 `image`，并将两者排除在上游视频轮询之外。
- Base64 图片在任务列表中转换为轻量预览地址，过期内容返回 HTTP 410。

## 3. 遇到的错误

1. 初版让普通 `/v1/images/tasks` 复用 `canvas_image` 平台，行为正确但语义不清，用户指出清理条件应显式覆盖通用任务。
2. 清理查询最初按最旧记录升序扫描，历史正文清空后可能重复跨过大量空记录。
3. classic 前端首次复验时，本地依赖目录缺少 Semi UI 的 CSS 导出。
4. 国际化同步工具将一个受保护项目键转为 Unicode 转义形式。
5. 固定本地测试数据库缺失，无法完成约定端口上的手工集成验证。

## 4. 根本原因分析

### 为什么会出现这些问题？

- 过度复用 Canvas 的既有实现，掩盖了普通令牌 API 与 Canvas 的来源差异。
- 清理实现先关注历史积压吞吐，没有充分考虑清理完成后的稳态查询成本。
- 前端依赖目录曾由不同工具链生成，安装状态与锁文件不完全一致。
- 国际化工具会规范化 JSON 键，未天然理解项目对特定标识的保护规则。

### 是什么导致编写时出现这些问题？

- 数据生命周期设计没有在第一版就把“来源平台”和“结果类型”拆开建模。
- 验证重点偏向功能正确性，性能审查是在后续代码复核中补齐的。
- 工作区存在并行功能改动和生成文件，增加了提交范围与工具状态审计难度。

## 6. 经验总结

### 核心洞察

- 数据清理条件应表达业务分类，而不应依赖来源命名的隐式复用。
- 大表清理不仅要关注首次积压，还要关注清空后的稳态扫描路径。
- 异步包装请求仍必须复用原有渠道选择、速率限制和计费链路。

### 预防策略

- 为本地异步任务维护统一的平台集合与判断函数。
- 清理任务测试同时覆盖历史积压、刚到期数据、批量上限及非目标平台。
- 发版前分别审查工作区差异与暂存区差异，禁止直接 `git add -A`。

### 识别的最佳实践

- 使用 GORM 的“先选主键、再更新”方案兼容 SQLite、MySQL 与 PostgreSQL。
- 清空大字段而保留任务行，兼顾空间复用与审计可追溯性。
- 多实例部署中仅主节点运行定时清理，并使用进程内互斥防止重入。

## 7. 知识提炼

### 可复用模式

- 本地异步包装器：立即返回任务 ID，后台复用原同步 Relay 链路。
- 结果数据保留：状态与审计长期保留，大正文按 TTL 独立清空。
- 稳态清理：从时间边界附近向历史方向处理，避免重复扫描已清理数据。

### 应避免的反模式

- 用一个来源特定的平台名承载所有同类任务。
- 为分批清理依赖数据库专属的 `UPDATE LIMIT` 语法。
- 在并行工作区中直接全量暂存或提交生成文件。

## 11. 2026-07-31 失败使用日志补齐

### 问题

本地异步图片包装器在成功时会复用同步图片结算链路写入消费日志，但失败终态只更新
`tasks.status=FAILURE` 和 `fail_reason`。因此无可用渠道、分配前校验失败、包装器超时或
后台异常不会稳定出现在普通使用日志；已经进入 Relay 的最终渠道错误还依赖
`ERROR_LOG_ENABLED`，造成“成功有使用日志、失败只有任务日志”的不一致。

模型广场的失败排除规则只控制 `perf_metrics` 样本，不参与 `tasks` 或 `logs` 写入，
本次修复不改变其语义。

### 契约

- `image` 与 `canvas_image` 任务一旦成功转换为 `FAILURE`，必须写入一条
  `logs.type=5` 错误日志，不受 `ERROR_LOG_ENABLED` 影响。
- 日志至少保存任务 ID、平台、动作、模型、渠道、分组、HTTP 状态码和失败原因；
  失败正文继续经过敏感信息遮罩。
- 异步包装器内部 Relay 的普通错误日志由任务终态日志接管，避免同一失败重复写入。
- 包装器超时与后台超时扫描使用任务状态 CAS；只有赢得终态更新的一方写日志，迟到
  响应或并发清理不得产生重复记录。
- 任务状态更新失败时记录服务器运行错误，并保留给后续超时扫描重试；不得假装已经
  写入失败使用日志。
- 上游返回 2xx 但正文为空时按网关失败记录，不得产生“任务失败但状态码成功”的日志。
- 不新增数据库专属 SQL 或结构迁移，继续兼容 SQLite、MySQL 和 PostgreSQL。

### 验证结果

- 错误日志全局开关关闭时，异步图片失败仍写入一条使用日志。
- 无渠道、上游非 2xx、包装器超时和后台超时扫描均覆盖失败日志。
- Relay 原错误入口与任务终态入口不会双写。
- CAS 失败或迟到响应不新增第二条失败日志。
- 成功任务仍只写原有消费日志，不新增错误日志。
- JSON、URL 编码表单和 multipart 三种请求均能保存原始模型名。
- `go test -count=1 -timeout 60s ./model ./service ./controller ./router` 通过。
- `go vet ./model ./service ./controller ./router` 与 `git diff --check` 通过。
