# 模型广场性能摘要布局与可用状态

## 问题

- Classic 卡片把计费标签、吞吐量、延迟、时间、状态条和成功率挤在左下同一行，信息拥挤。
- 状态条直接使用全部分组的汇总成功率。任一分组异常都可能把整张模型卡片显示为红色，容易被理解为该模型在所有分组均不可用。

## 方案

- Default 与 Classic 卡片统一在右下角按“延迟、吞吐量、状态”三列展示，标签在上、值在下。
  桌面端摘要宽度收紧为 `132px`，标签与数值使用弱化文字色，吞吐量采用紧凑的 `t`
  后缀，减少卡片底部的视觉重量。
- 模型卡片状态使用三段、由低到高的细圆柱信号条，柱宽 `4px`、间距 `2px`；不显示
  时间戳和整体百分比。Classic 性能详情保留最近 24 个原始状态点，Default
  性能详情保留原有逐点状态条和统计口径。
- 摘要接口新增可选字段 `status_rate`：
  - `data.models[].status_rate` 表示最近窗口内最佳可用分组的成功率；
  - `data.models[].series[].status_rate` 表示对应时间桶内最佳可用分组的成功率；
  - 原有 `success_rate` 继续表示全部请求的真实成功率，保持兼容。
- 模型广场状态分级：最佳分组成功率 `>= 95%` 为绿色；大于 `0%` 但低于 `95%` 为黄色；所有分组均为 `0%` 才为红色；没有样本为灰色。
- 当前分组 code 与历史别名先归并为同一分组，再计算最佳分组状态，避免迁移造成重复分组。

## 兼容与安全

- `status_rate` 为向后兼容的可选响应字段，旧前端会忽略；新前端在旧后端缺少字段时回退到 `success_rate`。
- 不改变性能指标采集、真实成功率、计费、渠道选择或重试逻辑。
- 批量摘要仍不返回分组名称、请求量、渠道、令牌或请求明细。

## 测试计划

1. 后端测试覆盖一个分组健康、一个分组不可用，以及所有分组均不可用。
2. Default 与 Classic 测试覆盖绿色、黄色、红色三种可用状态。
3. 执行 Go 相关包测试、Default 类型检查、两套前端相关测试与生产构建。
4. 使用固定本地测试入口验证桌面和窄屏卡片布局，完成后停止测试服务。
5. 执行修改文件格式检查及 `git diff --check`。

## 验证结果

- Go 性能摘要与分组别名测试通过，`go vet` 通过。
- Default 状态分级测试 `5/5`、卡片布局测试 `1/1` 通过；Classic 性能与布局测试
  `8/8` 通过。
- Default TypeScript 类型检查、Default 与 Classic 生产构建均通过。
- 使用固定本地环境 `3000/3001` 验证状态接口、Classic 首页、默认账号登录与演示数据
  接口；完成后已停止测试进程。
- 使用仅限浏览器展示的模拟摘要验证桌面与 `390px` 窄屏：三列摘要分别显示绿色、黄色、
  红色状态；综合成功率为 `50%`、最佳分组为 `100%` 时仍显示绿色。两种视口均无横向
  溢出。
- 参考 `zzshu.cc/pricing` 的实际计算样式复核模型卡片：摘要宽度 `132px`，状态柱宽
  `4px`、间距 `2px`、高度依次为 `8/10/12px`，圆角为胶囊形；浏览器实测桌面与窄屏
  均符合该尺寸。
