# 安全审计 cyber_policy 渠道与分组作用范围

## 目标

上游官方风控事件不再只能全局记录。Root 可以选择对全部渠道、多个指定渠道，或多个
业务分组生效。业务分组使用“分组管理”的稳定编码，不使用渠道标签或显示名称。

## 配置契约

内置安全策略接口新增以下字段：

- `upstream_policy_target_type`：`all`、`channels` 或 `groups`。
- `upstream_policy_channel_ids`：指定渠道 ID 数组。
- `upstream_policy_group_codes`：指定业务分组编码数组。

旧配置缺少这些字段时按 `all` 处理。渠道和分组模式必须至少选择一个目标；保存时规范化
重复值和空值。切换模式时保留其他模式的已选值，便于 Root 来回调整，但运行时只使用
当前模式对应的目标。

## 运行边界

结构化 `cyber_policy` 识别与内容策略标记始终全局执行，保证客户端原始响应、模型广场
失败排除和渠道质量口径不受作用范围影响。作用范围决定是否写入
`source=upstream_policy` 的安全审计事件；自动封禁只基于已写入的事件，因此自然遵循
同一范围。独立开启的会话阻断也复用该范围：只有范围内命中才建立标记，后续请求只在
本次实际路由仍位于范围内时读取。响应和每次重试使用本次实际选中的渠道及其业务分组
匹配，不能使用用户分组、渠道标签或旧的显示名称。

## 请求归档密钥边界

本地完整请求归档在未配置 `CRYPTO_SECRET` 时继续使用 Root-only 明文兼容格式，不得
恢复“启用完整请求归档前必须配置稳定密钥”的通用门禁。对象存储访问密钥仍属于必须
加密保存的凭据；配置或替换这类凭据仍要求稳定密钥，历史加密任务也仍需原密钥解密。

## 测试计划

1. 覆盖全部渠道、指定渠道、指定分组和不命中范围。
2. 覆盖跨渠道重试后按最终实际渠道匹配，以及分组编码解析。
3. 验证范围外 `cyber_policy` 仍设置内容策略标记，但不写审计事件或触发自动封禁。
4. 验证旧配置默认全局，并拒绝空的渠道/分组目标。
5. 验证无 `CRYPTO_SECRET` 时本地归档配置可保存、任务可写入和读取。
6. 验证 Default、Classic 的目标模式、渠道多选和分组多选保存一致。

## 实现结果

- 配置字段进入 `prompt_audit_configs` 单例配置和内置策略 CAS 保存链路，GORM 自动迁移
  继续兼容 SQLite、MySQL 和 PostgreSQL。
- 事件写入前按当前实际选中渠道匹配；分组模式只匹配本次请求最终实际使用的路由分组，
  不再因为同一渠道同时绑定其他分组而扩大范围。范围外命中不会占用事件去重键，因此
  后续重试切换到范围内渠道或分组时仍可正常记录。
- 会话阻断标记的写入和读取复用相同的实际渠道或分组匹配；跨重试切换路由后重新检查。
  缓存命名空间升级到 `v2`，隔离升级前可能由范围外命中产生的旧标记。
- 官方风控事件固化 `group_code`。事件列表累计次数和自动禁用都按当前作用范围过滤；
  指定分组模式不会把升级前缺少 `group_code` 的历史事件混入阈值。
- 保存指定分组范围时校验分组真实存在且已启用；运行时累计只使用规范化稳定编码。
- Default 和 Classic 均提供全部渠道、指定渠道、指定分组三种模式，支持多选、搜索、
  失效引用回显、加载失败重试和空目标校验，并补齐全部支持语言。
- 本地无密钥归档测试通过公开保存接口启用目标，并覆盖队列正文、Worker 本地落盘和
  最终正文读取，未引入通用 `CRYPTO_SECRET` 门禁。

## 验证结果

- Go 模型 CAS、内置策略保存、渠道与分组命中、跨重试范围判断及无密钥本地归档测试
  通过。
- Default 18 项安全审计测试、TypeScript 检查和生产构建通过；Classic 作用范围和 API
  专项测试、格式检查、八种语言完整性检查通过，Vite 已完成生产编译并生成输出。
- 固定环境复用 `tmp-local-v10101.db`，完成 `3000/3001` 状态、首页、Root/Demo 登录和
  演示数据验证。在 `crypto_ready=false` 下通过真实 API 保存并读取指定渠道范围，也能
  启用本地归档；随后恢复原配置并停止两个测试进程。
