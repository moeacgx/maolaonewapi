# 旧分组标识显式迁移为稳定 ID

## 背景

新建分组已经把数据库 ID 的十进制文本作为兼容 `code`，但升级前创建的分组仍可能使用
`group_2`、`group_3` 或其他旧标识。直接在启动时自动改写会影响令牌、渠道、能力表主键、
订阅快照和运行时选项，也不适合新旧实例混合运行，因此迁移必须由管理员显式执行。

## 接口

- `POST /api/group/code-migration/preview`：只读预检，返回迁移分组、影响数量和阻塞原因。
- `POST /api/group/code-migration`：请求体必须为 `{"confirm":true}`，事务内重新预检后执行。

两个接口均需要管理员权限。执行接口不会信任之前的预览结果，避免预览和执行之间出现新的
分组或历史别名冲突。

## 迁移范围

迁移所有非 `default` 且 `code` 不等于自身 ID 的实体分组，并同步处理：

- `groups.code`，同时写入“旧 code → 原分组 ID”的历史别名；
- 渠道和令牌的稳定分组绑定对应的字符串镜像；
- 令牌倍率保护，根据 `token_groups.ratio_limit` 重建，保留顺序且不会产生重复分组；
- 用户分组镜像和能力表复合主键中的分组字符串；
- 套餐升级分组、用户订阅升级分组及购买前分组快照；
- 分组倍率、可用分组、自动分组、组间倍率、充值倍率、特殊可用规则和模型限流选项；
- 屏蔽词规则中 `target_type=groups` 的 `group_codes`；渠道、渠道标签和全渠道规则不改写；
- 安全审计官方风控分组范围和自动封禁分组白名单，并通过 CAS 递增一次配置版本；
- 当前进程的运行时选项、渠道缓存、独立分组快照、令牌缓存、用户缓存及套餐缓存。

`default` 保留固定标识。日志、性能指标、渠道历史指标和安全审计事件等事实快照不直接
改写；模型广场、渠道分析和安全审计惩罚性累计查询会把当前 code 展开为“当前 code +
全部历史别名”，并把旧标识归并到同一稳定身份，因此迁移前后的历史统计、官方风控作用
范围和自动封禁豁免保持连续。迁移接口完成后立即失效安全审计配置缓存。
屏蔽词规则使用 `setting.ParseSensitiveRulesJSONString` 做结构化预检，并以
`SensitiveRuleConfig` 规范化保存；迁移事务提交后立即发布新的运行时屏蔽词策略快照。规则仍
引用某个分组当前 code 或历史 alias 时，分组删除会被拒绝，避免留下失效规则。
只要屏蔽词分组规则、官方风控分组范围或自动封禁白名单中任意一项发生改写，安全审计
`config_version` 都会在同一事务中通过 CAS 递增一次，旧管理页面保存时会得到版本冲突。

## 与令牌分组迁移的关系

旧 code 迁移只改写分组身份及其引用，不会删除或合并令牌记录。管理员通过
`POST /api/group/token-migration` 把令牌从源分组迁往目标分组时，如果某条令牌已经绑定目标
分组，只会删除该令牌内部重复的源分组绑定，并保留目标分组原有顺序和倍率保护；两条不同
令牌即使配置完全相同，也不会被系统合并或删除。

## 冲突与原子性

以下情况会阻止整笔迁移：

- 目标数字 code 已被其他分组当前 code 或历史别名占用；
- 某个旧 code 会成为另一分组的目标数字 code，导致历史别名无法安全保留；
- 旧 code 已被登记为其他分组的历史别名；
- 高级选项改写后出现同键冲突；
- 屏蔽词规则 JSON 或目标范围不合法；
- 能力表中同一稳定分组、渠道和模型存在多个不同旧标识。

分组、能力主键和全部镜像在同一数据库事务内更新。分组及能力字符串先切换到事务占位值，
再写最终数字 code，支持 SQLite、MySQL 和 PostgreSQL 的唯一键约束。执行失败时不保留部分
迁移结果。

## 部署与回滚边界

执行前必须确保所有实例已经升级到支持数字 code 和历史别名的同一版本。执行迁移时只能
保留负责执行的一个新版本实例，其他实例全部停止，并暂停分组、渠道、令牌、用户分组和
订阅套餐配置写入；迁移完成后再统一启动其他新版本实例。否则其他实例的旧内存选项与渠道
缓存可能在同步前短暂使用错误倍率或路由，旧版本实例还可能重新写入旧镜像。

需要回滚程序版本时，应先恢复迁移前数据库备份。不要仅手工把 `groups.code` 改回旧值，
因为能力复合主键、选项和各业务镜像已经同步迁移。
