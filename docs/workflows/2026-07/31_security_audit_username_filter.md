# 安全审计用户名筛选

## 问题

审计事件列表已经展示事件发生时保存的用户名，但筛选器仍要求 Root 输入数字用户
ID。审核员通常从列表看到的是用户名，必须额外查询用户 ID 才能过滤，且在账号改名
或删除后容易把当前账号信息和历史事件快照混淆。

## 目标与范围

- Default 与 Classic 的“用户 ID”数字输入改为“用户名”文本输入。
- 用户名支持忽略大小写的部分匹配。
- 列表、删除预览和确认删除复用同一个后端筛选条件。
- 保留后端 `user_id` 参数，兼容旧客户端和已有管理脚本；新页面不再提交该字段。
- 不改变事件表中的用户名快照，也不尝试关联当前用户表补写历史名称。

## 数据与接口契约

`GET /api/security-audit/events` 新增可选查询参数 `username`。删除预览与按筛选删除
请求中的 `filter` 同样接受 `username`。该值会清理首尾空白，并直接匹配
`prompt_audit_events.username`：

- 匹配语义为不区分大小写的“包含”；
- 筛选值最多 128 个 Unicode 字符，与事件用户名快照列的容量一致；
- `%`、`_` 和 `!` 按普通字符处理，不能成为数据库通配符；
- 同时传入 `username` 和旧的 `user_id` 时，两个条件按“且”组合；
- 空白用户名视为未提供条件，不能单独满足按筛选删除的最小条件限制；
- 删除确认令牌的筛选哈希包含规范化后的用户名，预览后修改用户名会使令牌失效。

选择事件用户名快照而不是关联当前用户表，是为了让筛选结果和列表显示严格一致，
并保留用户改名、删除后的审计可追溯性。

## 数据库兼容与安全边界

查询使用参数绑定和显式 `LIKE ... ESCAPE '!'`，先转义用户输入，再做小写比较，兼容
SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+。用户输入不会拼接到 SQL。接口权限保持
Root-only，响应继续使用 `Cache-Control: no-store`。

## 验证计划

- 模型测试覆盖部分匹配、大小写、`%`、`_`、`!` 转义和无匹配结果。
- 验证列表查询、删除预览和实际删除使用同一用户名条件。
- 验证查询参数与删除 JSON 都能接收并规范化 `username`。
- 验证两套前端显示用户名文本框，清理首尾空白后提交 `username`，且不再提交
  `user_id`。
- 执行相关 Go 测试、前端专项测试、类型检查/代码检查、生产构建与
  `git diff --check`；无法执行的既有工具问题需在交付说明记录。
