# 管理员调整余额的目标用户日志可见性

## 问题

管理员在用户管理中增加、扣减或覆盖用户余额后，管理审计日志归属于操作管理员。
Classic 管理日志按目标用户名筛选时无法命中，目标用户通过自己的日志接口也无法核对余额变更。

## 根因

`recordManageAuditFor` 将所有用户管理审计统一归属实际操作者。目标用户 ID 仅保存在
`other.op.params.target_user_id`，而日志列表按 `logs.user_id` 或 `logs.username` 查询，
因此目标用户范围不会返回该记录。

## 修复范围

- 仅将 `user.quota_add`、`user.quota_subtract` 和 `user.quota_override` 三类余额操作日志
  归属目标用户，恢复 v243 的用户可核对行为。
- 其他用户管理、渠道和系统操作继续归属实际操作者，不扩大用户可见范围。
- 每次余额操作只写一条日志，避免管理员全量列表和导出出现重复记录。
- 数据库原始日志继续在 `admin_info` 中保留操作管理员身份和请求 IP。
- 用户日志响应移除 `admin_info`、`audit_info` 和管理日志 IP，避免暴露管理员身份与网络信息；
  结构化操作类型和余额变化继续可见。

## 兼容性

该变更只调整日志行的归属用户和用户响应脱敏，不修改数据库结构或 API 路径。
实现使用现有 GORM 查询和日志字段，兼容 SQLite、MySQL 与 PostgreSQL。

Default 与 Classic 均使用相同的 `/api/log`、`/api/log/self` 后端契约，因此两套模板都会恢复
目标用户余额管理日志可见性，无需分别修改前端。

Classic 会根据 `other.op.action` 在展示时本地化增加、扣减和覆盖额度三类操作，避免中文界面
直接显示后端的英文兜底内容。相关文案覆盖 Classic 支持的全部语言资源。

## 验证

- Root 为普通用户增加余额后，余额正确更新。
- 数据库仅存在一条目标用户归属的 `type=3` 日志。
- 原始日志包含管理员审计信息，目标用户查询结果不包含管理员信息和 IP。
- 目标用户查询结果保留 `user.quota_add` 结构化操作信息。
- Classic 简体中文将 `user.quota_add` 展示为“管理员增加用户额度”，其他余额操作同样按当前语言展示。
