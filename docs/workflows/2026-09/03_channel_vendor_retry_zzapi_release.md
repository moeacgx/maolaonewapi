# 渠道供应商与上游重试 `.303` 发布记录

## 目标与范围

- 发布版本：`v1.0.0-rc.10.1.10.303`。
- 变更基线：`v1.0.0-rc.10.1.10.302...v1.0.0-rc.10.1.10.303`。
- 渠道管理：恢复 `vendor_id` 保存、详情回填、显式清除、供应商计数与筛选，并恢复
  Default 渠道编辑和列表展示。
- 中继重试：恢复嵌入错误文本中的可信上游状态码识别，并在失败时驱逐失效的渠道亲和缓存。
- 部署目标：仅 CloudSSH 项目“API中转站”的 `serverId=52`，Compose 目录
  `/home/docker/zzapi`。
- 应用服务：`zzapi-slave-1`、`zzapi-slave-2`、`zzapi`，按此顺序逐个滚动更新。
- 明确不更新：`zzapi-postgres`、`zzapi-redis` 和受保护的 `maolaoapi`。

## 兼容性与安全边界

- 渠道迁移只新增可空的 `vendor_id` 及普通索引，SQLite、MySQL 和 PostgreSQL 均由 GORM
  迁移；旧版本可忽略该列，因此允许 `.302` 与 `.303` 在滚动窗口内短时并存。
- 更新接口中省略 `vendor_id` 表示保留绑定，数字表示设置绑定，显式 `null` 表示清除绑定。
- 供应商字段属于普通渠道元数据，不因敏感渠道写权限缺失而锁定；密钥等敏感字段权限保持不变。
- 回滚应用版本时新增数据库列可以保留，不执行删列或数据库恢复。

1. PR `#159` 的后端、前端与质量检查全部通过后合并到 `custom-main`。
2. 等待 PR 合并触发的 `closed` 事件 CI 在远程主分支再次通过。

   多架构镜像工作流成功。
4. 核对 Release 二进制、校验文件、`linux/amd64`、`linux/arm64` 和版本镜像 manifest。

## 远端更新与验收

1. 更新前读取 Compose 项目、应用镜像、容器状态、重启次数、本地端口和公网状态。
2. 记录 `.302` 镜像不可变摘要，并创建带版本号的 Compose 备份。
3. 只把三个应用服务的镜像标签更新为 `.303`，逐个执行无依赖强制重建；每个节点验证
   `running/healthy`、重启次数 `0`、容器内版本和本地 `/api/status` 后再继续。
4. 全部节点完成后核对 `18097/18098/18099`、公网 `/api/status`、Nginx 分流和启动日志。
5. 使用 Root 登录态验证新建或编辑渠道可保存供应商，重新打开仍能回填，列表供应商列与顶部
   供应商筛选均正确；再执行一次低成本鉴权请求验证基础中继链路。

## 回滚

任一节点更新失败时立即停止后续节点，使用发布前记录的 `.302` 镜像摘要和 Compose 备份，
仅回滚已修改的应用服务。不得重建 PostgreSQL、Redis，不得操作 `maolaoapi`；回滚后重新
核对三个应用端口、容器健康、重启次数和公网状态。
